参考回答：

这个功能主要是为了实现域名映射管理的自动化。

传统方式下，如果需要新增域名映射，可能需要人工修改 CoreDNS 的配置文件。

我们通过 Kubernetes CRD 扩展了一个 DomainMapping 资源，用户可以通过 API 创建域名映射请求，然后由 Controller 自动完成后续配置同步。

整体流程是：

1. 用户通过 API 创建 DomainMapping 资源。
2. Kubernetes API Server 保存资源。
3. Informer 监听资源变化，并通过 EventHandler 将资源 Key 放入 WorkQueue。
4. Worker 从 WorkQueue 获取任务。
5. 通过 Lister 从本地缓存中获取 DomainMapping 对象。
6. 执行 Reconcile，检查期望状态与实际状态。
7. 将域名映射配置同步到 CoreDNS。
8. 最后更新 DomainMapping 的 Status。

这样就形成了从 API 请求到 DNS 配置同步的自动化流程。

### Q3：为什么要使用 Informer 和 WorkQueue？直接监听 Kubernetes 事件不行吗？

参考回答：

主要是为了实现事件监听和业务处理的解耦。

Informer 负责监听 Kubernetes 资源变化，并通过本地缓存减少频繁访问 API Server 的开销。

EventHandler 负责接收资源变化事件，但不直接执行复杂的业务逻辑，而是将资源的 Namespace 和 Name 放入 WorkQueue。

Worker 再从队列中获取任务，通过 Lister 读取最新资源状态，执行具体的 Reconcile。

这样有几个好处：

1. 事件处理和业务处理解耦。
2. WorkQueue 可以实现任务去重和限速重试。
3. 可以通过多个 Worker 并发处理任务。
4. 不需要每次都直接请求 API Server 获取资源。

另外，事件本身只是一个触发信号，真正的处理依据应该是资源当前的最新状态。

### Q4：Reconcile 是什么？为什么需要不断调谐？

参考回答：

Reconcile 的核心思想是让实际状态逐渐收敛到期望状态。

例如用户创建了一个 DomainMapping，期望 CoreDNS 中存在对应的域名映射。

但是资源创建成功，并不代表 CoreDNS 配置一定已经同步成功。

可能存在网络异常、配置更新失败或者其他组件暂时不可用等情况。

因此 Controller 需要不断比较期望状态和实际状态，并执行必要的操作。

Reconcile 应该尽量保证幂等性，也就是相同的期望状态执行多次，不应该产生额外副作用。

如果某次执行失败，可以通过 WorkQueue 的重试机制再次调谐。

### Q5：如果 CoreDNS 配置更新失败怎么办？

参考回答：

我会把整个流程拆成资源状态和实际配置两个部分。

首先，DomainMapping 资源已经写入 Kubernetes，说明用户的请求已经被接受。

如果 CoreDNS 配置同步失败，就不能直接把资源标记为成功。

应该保留当前失败信息，在 Status 中记录对应的处理状态和错误原因。

同时让 Reconcile 返回错误或者采用适当的重试机制，使 WorkQueue 能够重新调度任务。

下一次执行时，重新读取最新的 DomainMapping，判断实际配置是否已经满足期望状态，如果没有，就继续执行同步。

这里需要注意幂等性，避免重复写入导致配置异常。

### Q6：CRD 和 Controller 分别是什么？两者是什么关系？

参考回答：

CRD 是 Custom Resource Definition，用于扩展 Kubernetes API，让用户可以定义自己的资源类型。

Controller 是控制器，负责监听这些自定义资源，并协调实际状态。

两者的关系可以理解为：

- CRD 定义资源的数据结构和 API。
- Custom Resource 是用户创建的具体资源对象。
- Controller 负责监听和处理这些对象。

例如我们的 DomainMapping：

CRD 定义域名映射资源的字段，用户创建 DomainMapping 对象，Controller 监听这个对象，然后完成 CoreDNS 配置同步。

CRD 本身不会自动执行任何业务逻辑，真正的自动化行为是由 Controller 实现的。

### Q7：你开发 Helm Chart 的时候主要做了什么？

参考回答：

主要是将 Kubernetes 组件所需的资源进行模板化和标准化。

例如 Longhorn 组件，部署时需要涉及多个 Kubernetes 资源。

我主要是将这些资源整理到 Chart 中，通过 values.yaml 提供可配置参数，然后在 templates 中定义对应的资源模板。

这样可以将组件的部署参数和资源定义分离。

用户可以根据不同环境调整配置，通过 Helm 实现统一安装和升级，而不需要每次手动维护大量 YAML 文件。

### Q9：Go 中如何实现一个协程池？

参考回答：

可以使用固定数量的 Goroutine 加一个带缓冲的 Channel 实现简单的 Worker Pool。

基本结构包括：

- Job Channel：负责接收任务。
- Worker：固定数量的 Goroutine，从 Channel 中获取任务。
- Result：根据业务需要返回处理结果。
- Context：负责取消任务和控制生命周期。

这样可以避免为每个任务无限创建 Goroutine。

另外，还需要考虑：

1. Channel 缓冲区大小。
2. Worker 数量。
3. 任务超时。
4. Context 取消。
5. 优雅关闭。
6. 队列满时的背压处理。

Worker 数量不应该简单地越多越好，需要结合 CPU、内存和下游服务的处理能力进行调整。

### Q10：如果 Goroutine 数量不断增加，你会怎么排查？

参考回答：

首先会通过 pprof 查看 Goroutine Profile，分析当前 Goroutine 的数量和调用栈。

重点关注：

- 是否存在 Goroutine 泄漏。
- 是否有 Goroutine 阻塞在 Channel 读写。
- 是否存在锁竞争。
- 是否有网络请求一直没有超时。
- 是否缺少 Context 取消机制。

如果是业务任务堆积，还需要检查生产速度和消费速度是否不匹配。

可以通过增加限流、控制 Worker 数量、设置超时以及引入背压机制解决。

### Q11：你自己实现的 errx 错误库有什么特点？

参考回答：

主要是为了提供更方便的错误链和调用栈管理能力。

Go 标准库已经提供了 error、Unwrap 和 errors.As 等错误处理机制。

我在此基础上增加了调用栈捕获和统一格式化输出。

底层通过 runtime.Callers 捕获调用栈。

另外，在直接包装已有 StackError 时，会复用原来的调用栈，避免每次包装错误都重新捕获堆栈。

这样既保留了标准库的错误链兼容性，也减少了重复的堆栈信息。

### Q12：Context 在 Go 项目中主要解决什么问题？

参考回答：

Context 主要用于在多个 Goroutine 和调用链之间传递取消信号、超时和请求级别的上下文信息。

例如一个 HTTP 请求可能会触发多个下游服务调用。

如果客户端提前断开连接，就可以通过 Context 将取消信号传递给下游任务，避免继续执行无效工作。

在实际开发中，我主要会在网络请求、异步任务和 Worker Pool 中使用 Context。

## 第三部分：Kubernetes 与云原生

### Q13：Pod 一直处于 CrashLoopBackOff，你怎么排查？

参考回答：

我一般会按照从外到内的顺序排查。

首先使用 kubectl describe pod 查看 Pod 事件，确认是否存在镜像拉取、调度、挂载或者探针失败等问题。

然后使用 kubectl logs --previous 查看上一次容器退出前的日志。

接下来根据具体情况检查：

1. 容器启动命令和环境变量。
2. ConfigMap 和 Secret 挂载。
3. 依赖服务是否正常。
4. 数据库连接是否成功。
5. 容器资源限制和 OOM 情况。
6. LivenessProbe 和 ReadinessProbe 配置。

如果是容器内部程序启动失败，还需要结合应用日志和退出码进一步定位。

### Q14：Kubernetes Service 无法访问，你怎么排查？

参考回答：

我会从 Service 到 Pod，再到网络层逐步排查。

首先检查 Service 是否存在，以及 selector 是否能够匹配目标 Pod。

然后检查 EndpointSlice 或 Endpoints，确认是否已经关联到正确的 Pod IP。

接着检查 Service 的 port 和 targetPort 是否正确，Pod 内应用是否真的监听对应端口。

如果这些都正常，再继续排查：

- Pod 内 DNS 解析。
- NetworkPolicy。
- CNI 网络连通性。
- 节点之间的网络。
- kube-proxy 或对应的数据面转发机制。

通过逐层排查，可以缩小问题范围。

### Q15：Helm 和 Kubernetes 原生 YAML 有什么区别？

参考回答：

Kubernetes YAML 主要描述具体的资源对象，而 Helm 是 Kubernetes 的包管理工具。

Helm 通过 Chart 将多个 Kubernetes 资源组织在一起，并通过模板和 Values 实现参数化。

相比直接维护 YAML，Helm 更适合组件化交付，可以实现：

- 资源模板化。
- 参数配置复用。
- 版本管理。
- 安装与升级。
- 回滚。

所以在平台产品中，通常可以使用 Helm 统一管理应用组件的交付。

### Q16：你们为什么使用 Hyperscan？普通正则不行吗？

参考回答：

普通正则表达式可以满足基本的模式匹配需求，但在大量日志字段和多规则匹配的场景下，性能可能成为瓶颈。

Hyperscan 是一个高性能正则表达式匹配库，主要优势是支持多模式匹配，并且利用 SIMD 等技术优化匹配性能。

在我们的 API 风险监测平台中，需要对 HTTP 日志字段进行大量模式识别和打标，因此引入 Hyperscan 来实现正则匹配。

它更适合需要同时执行大量匹配规则的场景。

### Q17：你们为什么使用 K-means 做 API 聚合？

参考回答：

主要是因为不同 API 可能在路径参数等方面存在差异，但实际上属于同一类业务接口。

如果完全依靠字符串匹配，可能无法准确识别这些接口之间的相似性。

因此引入 K-means 聚类算法，对 API 进行特征表示，然后根据特征之间的距离进行分组，实现相似 API 的聚合。

K-means 的优点是实现相对简单，适合进行无监督聚类。

不过它需要提前确定 K 值，而且聚类效果比较依赖特征工程和距离度量方式。

### Q18：为什么中文地址校验要使用 Transformer？

参考回答：

主要是因为正则表达式虽然可以提取候选地址，但很难准确判断一个地址是否真实有效。

例如，一段文本可能符合地址的基本格式，但实际上并不是一个有效的地址。

因此采用了规则提取加模型校验的方式。

首先使用正则表达式提取候选地址，然后将候选地址输入 Transformer Encoder，通过全连接分类层判断其有效性。

这样可以结合规则的可解释性和模型对上下文特征的学习能力，提高地址校验的准确性。

我主要把 AI 用在软件开发的多个阶段，而不是仅仅用于代码补全。

- 平台稳定性和可观测性。

这个问题可以判断团队是否真的存在有价值的技术问题需要解决。

## 第二优先级：研发深度

3. 团队目前的开发模式是什么？

可以继续问：

- 是否有完善的代码 Review？
- 是否有单元测试和集成测试？
- 是否有独立的测试环境？
- 开发人员是否负责完整的需求交付？
- 团队目前使用哪些技术栈？有没有自研的 Operator、Controller 或者平台基础组件？

这个问题可以帮助你判断是否能继续积累 Kubernetes 平台研发经验。

## 第三优先级：团队与发展

5. 这个岗位入职后的前三个月，通常希望新人完成哪些工作？

这个问题非常实用。

如果对方回答：

- 熟悉业务，参与核心模块开发：比较好。
- 主要负责部署、维护和现场支持：需要进一步判断。
- 独立承担某个 Controller 或平台模块：值得重点关注。
- 团队未来一年在技术方向上有什么规划？

可以判断团队未来是继续做传统平台，还是向 AI Infra、模型服务、云原生基础设施等方向发展。



问题 1：团队目前 AI 辅助研发的使用情况怎么样？

推荐这样问：

> 想了解一下团队目前在 AI 辅助研发方面的实践情况。比如是否已经在需求分析、代码开发、测试或者问题排查等环节使用 AI 工具或 Agent？目前主要使用哪些工具，整体的使用程度怎么样？

如果面试官回答比较积极，可以进一步追问：

> 团队目前是个人自主选择 AI 编码工具，还是公司有统一采购的工具或者内部部署的模型平台？对于 AI 生成代码的 Review 和质量保障，有没有相应的规范？

问题 2：团队是否有 AI Agent 或自动化研发方面的探索？

> 我自己平时比较关注 AI 工程化，也会使用 AI 辅助需求分析、编码和测试。想了解一下团队有没有进一步探索 AI Agent，比如自动化代码开发、测试、故障诊断或者研发流程自动化？

这两个问题分别考察：

- AI 是否真正融入日常研发，而不是停留在尝试阶段。
- 团队是否在探索 Agent 化研发，以及有没有相应的工程基础设施。
