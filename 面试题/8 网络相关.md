# 1、TCP协议

TCP 三次握手是网络面试的基础高频题。对于 WAF 控制面开发，还需要掌握连接异常、SYN Flood、半连接队列和 TCP 状态管理。

## 一、TCP 三次握手的完整过程

TCP 三次握手主要用于建立双向连接、同步初始序列号以及协商 TCP 参数。

### 第一次握手：客户端发送 SYN

客户端发送：

```
SYN = 1
seq = x
```

表示客户端希望建立连接，并告知服务端自己的初始序列号 ISN。

客户端状态：

```
CLOSED → SYN_SENT
```

### 第二次握手：服务端返回 SYN + ACK

服务端收到 SYN 后回复：

```
SYN = 1
ACK = 1
seq = y
ack = x + 1
```

这里有两个作用：

- `ack=x+1`：确认客户端发送的 SYN。
- `seq=y`：告诉客户端服务端自己的初始序列号。

服务端进入 `SYN_RCVD` 状态。

### 第三次握手：客户端发送 ACK

客户端收到 SYN+ACK 后回复：

```
ACK = 1
seq = x + 1
ack = y + 1
```

客户端发送第三次握手后进入 `ESTABLISHED`。

服务端收到有效 ACK 后，也进入 `ESTABLISHED`。

此时连接建立完成。

为什么 SYN 会消耗一个序列号？

TCP 的 SYN 和 FIN 控制标志各占用一个序列号，即使它们没有携带应用数据。

## 二、为什么必须三次握手，不能两次？

核心原因是：双方需要确认初始序列号已被正确接收，并避免将旧的重复连接请求误当成新的有效连接。

假设只使用两次握手：

```
Client ───── SYN ─────> Server
Client <── SYN+ACK ─── Server
```

服务端回复之后就直接认为连接建立成功。

但此时服务端还不知道客户端是否收到了自己的 SYN 和初始序列号。

例如网络中存在一条延迟到达的旧 SYN：

1. 客户端之前发送过一个连接请求，但该 SYN 在网络中长时间延迟。
2. 客户端重试或放弃了这次连接。
3. 旧 SYN 后来到达服务端。
4. 如果只需要两次握手，服务端可能在回复后直接建立一个客户端并不打算使用的连接。
5. 这会造成无效的连接状态和资源消耗。

采用三次握手后，服务端需要收到客户端对本次 SYN 的有效 ACK，才能确认连接建立。

更严格地说，三次握手完成了双方初始序列号的交换与确认，并帮助识别过期的连接请求。

面试时不要只回答“因为要确认双方的收发能力”，这只是便于记忆的简化说法，解释不够深入。

## 三、第三次握手的 ACK 丢失了怎么办？

这是面试官很喜欢的追问。

假设：

```
Client                 Server
   │                      │
   ├──── SYN ────────────>│
   │<──── SYN+ACK ────────┤
   │                      │
   ├──── ACK ────────X    │
   │                      │
```

此时双方状态不同：

| 端点   | 状态          |
| ------ | ------------- |
| 客户端 | `ESTABLISHED` |
| 服务端 | `SYN_RCVD`    |

接下来：

情况一：服务端等待超时

服务端可以重传 SYN+ACK。

客户端如果再次收到合法的 SYN+ACK，会回复 ACK。

当服务端收到 ACK 后，进入 `ESTABLISHED`。

情况二：客户端紧接着发送数据

客户端已经进入 `ESTABLISHED`，可以发送应用数据。

如果服务端接收到序列号及确认号合法的数据报文，通常也能够完成连接建立，而不一定必须收到原先丢失的那个纯 ACK 报文。

情况三：始终没有收到有效确认

服务端经过有限次数重传或超时后，会清理尚未建立的连接状态。

因此不能简单说第三次握手 ACK 丢失就一定导致连接失败。

## 四、TCP 连接建立过程中有哪些重要状态？

| TCP 状态      | 作用                            |
| ------------- | ------------------------------- |
| `CLOSED`      | 没有连接                        |
| `LISTEN`      | 服务端监听连接                  |
| `SYN_SENT`    | 客户端已发送 SYN                |
| `SYN_RCVD`    | 服务端已收到 SYN 并发送 SYN+ACK |
| `ESTABLISHED` | 连接建立完成                    |

Linux 排查命令：

```
ss -ant
```

查看指定端口：

```
ss -ant '( sport = :443 or dport = :443 )'
```

查看监听：

```
ss -lntp
```

如果服务端存在大量 `SYN_RECV` 连接，可以检查是否存在正常连接激增、丢包、ACK 未到达或 SYN Flood 等问题，不能仅根据数量直接判定遭受攻击。

## 五、WAF 面试延伸：SYN Flood 是什么？

SYN Flood 是一种利用 TCP 连接建立流程消耗服务端资源的 DoS/DDoS 攻击方式。

攻击者发送大量 SYN，造成服务端维护大量尚未完成握手的连接状态。

常见防护措施：

- SYN Cookies。
- 连接建立速率限制。
- 合理调整 TCP 连接相关队列。
- 上游 DDoS 防护或清洗。
- 根据部署架构使用 SYN Proxy。

特别注意：SYN Flood 是传输层攻击，而传统 WAF 主要负责 HTTP/HTTPS 应用层安全。

虽然某些一体化安全产品也具有 SYN Flood 防护能力，但不能认为所有 WAF 都能直接解决这种攻击。

## 六、90 秒面试参考答案

> TCP 通过三次握手建立连接。
>
> 首先客户端发送 SYN 和初始序列号 x，进入 SYN_SENT。
>
> 服务端收到后，回复 SYN+ACK，确认号为 x+1，并携带自己的初始序列号 y，进入 SYN_RCVD。
>
> 客户端收到后发送 ACK，确认号为 y+1，进入 ESTABLISHED。服务端收到有效确认后也进入 ESTABLISHED。
>
> 三次握手的核心目的是同步并确认双方的初始序列号，同时避免旧的重复连接请求导致服务端错误建立连接。
>
> 如果第三次 ACK 丢失，客户端已经进入 ESTABLISHED，服务端仍在 SYN_RCVD。服务端可以重传 SYN+ACK，客户端再次确认；如果客户端发送了携带有效 ACK 的数据报文，也可能完成服务端的连接建立。
>
> 在实际项目中，如果发现大量 SYN_RECV，我会检查连接建立速率、丢包、网络延迟和 SYN Flood 风险，同时结合 SYN Cookies、连接速率限制等机制进行防护。

## 七、TCP 面试高频追问

| 问题                              | 回答核心                                                   |
| --------------------------------- | ---------------------------------------------------------- |
| SYN 为什么消耗一个序列号？        | TCP SYN 在序列号空间中占用一个位置                         |
| 为什么不是两次握手？              | 无法确认服务端 SYN 已被对端收到，旧 SYN 也可能产生无效状态 |
| 为什么不是四次握手？              | SYN 和 ACK 可以合并发送，三次通常已经足够                  |
| 第三次 ACK 丢失怎么办？           | 重传 SYN+ACK，或通过后续有效报文完成确认                   |
| SYN Flood 怎么防？                | SYN Cookies、SYN Proxy、限速、上游 DDoS 防护               |
| TCP 握手完成后是否立即发送 HTTP？ | 可以，通常先进行 TLS 握手（HTTPS），再发送 HTTP 请求       |

下一题：TCP 四次挥手、TIME_WAIT、CLOSE_WAIT，以及为什么服务端可能出现大量 CLOSE_WAIT 连接。

对于 Go 后端和 WAF 控制面开发，这一题比单纯背四次挥手更实用，因为它涉及 HTTP 连接泄漏、服务端资源耗尽和线上故障排查。



# 2、HTTP、HTTPS 与 TLS

这部分比 TCP 四次挥手更贴近你要面试的 WAF 控制面开发岗位。WAF 主要处理 HTTP/HTTPS 流量，因此面试官不仅可能问协议基础，还可能追问 HTTP 解析、TLS 解密、反向代理和请求走私等问题。

建议重点掌握下面 8 道题。

## 一、HTTP 和 HTTPS 有什么区别？

HTTP 是应用层协议，用于客户端和服务器之间传输请求与响应。

HTTPS 通常是 HTTP over TLS，通过 TLS 为 HTTP 通信提供加密和身份认证。

| 维度             | HTTP                       | HTTPS                                               |
| ---------------- | -------------------------- | --------------------------------------------------- |
| 默认端口         | 80                         | 443                                                 |
| 加密             | 默认不加密                 | 使用 TLS 加密                                       |
| 身份验证         | 不提供 TLS 身份认证        | 通常验证服务端证书                                  |
| 完整性保护       | 不提供加密完整性保护       | TLS 提供完整性保护                                  |
| 传输协议         | 常见 TCP，也可采用其他映射 | HTTP/1.1、HTTP/2 通常基于 TLS/TCP；HTTP/3 基于 QUIC |
| 中间设备检查内容 | 通常可直接读取明文         | 需要在 TLS 终止点获得明文                           |

面试追问：HTTPS 能保证绝对安全吗？

不能。HTTPS 保护的是传输过程，不保证服务器本身没有 SQL 注入、XSS、越权等漏洞。

另外，HTTPS 通常也不会隐藏目标 IP、流量大小和通信时间等元数据。

## 二、HTTP/1.1、HTTP/2、HTTP/3 有什么区别？

简化协议栈：HTTP/3 将 TLS 1.3 握手集成在 QUIC 协议中。

### HTTP/1.1

特点：

- 持久连接（Keep-Alive）。
- 支持 Chunked Transfer Encoding。
- 支持请求流水线，但实践中较少使用。
- 同一连接上通常需要按请求顺序处理响应。

HTTP/1.1 存在应用层队头阻塞问题。

### HTTP/2

核心改进：

- 二进制分帧。
- 多路复用。
- HPACK Header 压缩。
- Stream 级流量控制。
- 在一个 TCP 连接中并发承载多个请求。

追问：HTTP/2 是否彻底解决队头阻塞？

没有。

HTTP/2 解决了 HTTP/1.1 的一部分应用层队头阻塞问题，但底层仍使用 TCP。发生丢包时，TCP 按序交付机制可能阻塞同一连接上的其他 Stream。

### HTTP/3

HTTP/3 运行在 QUIC 上。

QUIC 基于 UDP 实现可靠传输，并提供：

- 多条独立 Stream。
- TLS 1.3 安全握手。
- 连接迁移。
- 减少跨 Stream 的传输层队头阻塞。

面试加分点：HTTP/3 使用 UDP，不代表它不可靠。可靠性由 QUIC 自己实现。

## 三、一次 HTTPS 请求经历什么过程？

这是我认为 WAF 岗位最值得掌握的一道题。

假设浏览器请求：

```
https://example.com/api/users
```

主要过程：

1. DNS 查询

   将 `example.com` 解析为目标 IP 地址。

2. 建立传输连接

   如果使用 TCP，则执行三次握手。若使用 HTTP/3，则走 QUIC 的连接建立过程。

3. TLS 握手

   协商 TLS 版本、密码套件、密钥材料，并验证服务端身份。

4. 发送 HTTP 请求

   请求通过 TLS 加密后传输。

5. WAF 或代理处理

   如果 WAF 位于 TLS 终止点，可以解析 HTTP 请求并执行检测。

6. 后端处理

   应用服务器执行业务逻辑，返回 HTTP 响应。

7. 响应返回

   响应经过相应代理及 TLS 保护链路返回客户端。

这里需要注意，浏览器不一定每次请求都重新执行 DNS 查询、TCP 握手和 TLS 握手，因为可能复用现有连接或缓存。

## 四、TLS 1.3 握手过程是什么？

TLS 是 HTTPS 的安全基础。

当前面试建议重点掌握 TLS 1.3，同时了解 TLS 1.2 与 TLS 1.3 的区别。

### TLS 1.3 的主要过程

第一步：ClientHello

客户端发送：

- 支持的 TLS 版本。
- 密码套件。
- 随机数。
- 密钥交换参数（如 ECDHE Key Share）。
- SNI（目标主机名，若使用）。
- ALPN（如 `h2`、`http/1.1`）。

第二步：ServerHello

服务端选择双方支持的参数，提供自己的密钥交换信息。

双方通过 ECDHE 和 TLS 密钥派生机制计算后续通信所需的密钥。

第三步：服务器身份验证

服务端发送证书链、签名证明等握手信息。

客户端验证：

- 证书链是否可信。
- 证书是否在有效期内。
- 域名是否匹配。
- 证书用途及签名是否满足验证要求。

第四步：Finished 验证

双方发送 Finished 消息，验证握手完整性与密钥协商结果。

完成后，使用协商得到的对称密钥保护应用数据。

### 面试官可能追问：HTTPS 为什么同时使用非对称密码和对称密码？

因为它们解决的问题不同。

- 非对称密码学用于身份认证和安全密钥协商等。
- 对称加密用于高效保护实际的 HTTP 数据。

需要避免一个过时说法：“HTTPS 是用服务器公钥直接加密一个随机对称密钥传给服务器。”

这是对部分旧版 RSA 密钥交换的简化描述，不是现代 TLS 1.3 使用的方式。

TLS 1.3 通常通过 ECDHE 实现密钥协商。

## 五、TLS 1.2 和 TLS 1.3 的区别

| 特性         | TLS 1.2                     | TLS 1.3                         |
| ------------ | --------------------------- | ------------------------------- |
| 完整握手往返 | 典型约 2 RTT                | 典型约 1 RTT                    |
| 密钥交换     | 支持多种机制，包括旧式 RSA  | 使用现代（EC）DHE 或 PSK 等机制 |
| 前向保密     | 取决于密码套件              | 新建的标准密钥交换通常提供      |
| 密码套件     | 选择范围广，包含较旧机制    | 精简为现代 AEAD 加密套件        |
| 0-RTT        | 不支持标准 TLS 1.3 式 0-RTT | 会话恢复时可选支持              |

追问：0-RTT 有什么安全风险？

0-RTT 早期数据可能面临重放风险。

因此，不适合在缺少额外保护的情况下执行具有不可重复副作用的敏感操作。

## 六、WAF 如何检查 HTTPS 加密流量？

这是你面试该岗位必须掌握的问题。

HTTPS 请求在网络上是加密的，WAF 如果只是旁路观察密文，并不能直接看到 HTTP 请求的完整内容。

一种常见方案是 TLS Termination（TLS 终止）。

```
Browser
   │
   │ HTTPS
   ▼
┌──────────────────────┐
│       WAF            │
│                      │
│  TLS Termination     │
│         ↓            │
│  HTTP Request Parser │
│         ↓            │
│  Security Rules      │
│         ↓            │
│  Allow / Block       │
└──────────────────────┘
   │
   │ HTTP 或重新建立 HTTPS
   ▼
Backend Server
```

此时：

1. 客户端与 WAF 建立 TLS 连接。
2. WAF 作为 TLS 终止点解密请求。
3. WAF 解析 HTTP 内容，执行规则检测。
4. 合法请求转发到后端。
5. 如果后端使用 HTTPS，WAF 再建立独立的 TLS 连接。

面试追问：WAF 是否必须持有网站证书私钥？

对于常见的反向代理 TLS 终止方案，WAF 需要使用与目标域名匹配的有效证书及对应的私钥能力。

但具体实现可能通过本地私钥、HSM、远程签名等方式提供密钥操作能力，并不一定要求私钥明文保存在 WAF 进程中。

另外，旁路检测、与网关集成、在 TLS 终止点之后检测等部署方式也存在，不能把所有 WAF 都理解成独立的 HTTPS 反向代理。

## 七、HTTP Request Smuggling 是什么？

这是 WAF、网关和反向代理面试中非常有价值的进阶题。

HTTP Request Smuggling（HTTP 请求走私）主要与前端代理和后端服务器对请求消息边界的解析不一致有关。

例如 HTTP/1.1 存在不同的请求体长度描述机制：

```
Content-Length: 100
```

以及：

```
Transfer-Encoding: chunked
```

如果两个 HTTP 组件对报文边界的处理不一致，就可能发生请求边界错位。

这可能带来：

- 绕过安全检测。
- 请求混淆。
- 缓存污染。
- 非预期的后端请求执行。

对于 WAF 研发，重点不是只记住漏洞名称，而是理解：

WAF 和后端必须尽量保持一致的 HTTP 解析语义，并拒绝存在歧义或不符合协议规范的请求。

常见工程措施包括严格协议解析、拒绝冲突的消息长度描述、规范化转发，以及测试代理链中的协议转换行为。

## 八、Go 开发者需要熟悉的 HTTP 实现

Go 标准库提供：

```
net/http
```

例如一个简单的 HTTP Server：

```
package main

import (
    "fmt"
    "log"
    "net/http"
    "time"
)

func main() {
    mux := http.NewServeMux()

    mux.HandleFunc("/health", func(
        w http.ResponseWriter,
        r *http.Request,
    ) {
        fmt.Fprintln(w, "ok")
    })

    server := &http.Server{
        Addr:              ":8080",
        Handler:           mux,
        ReadHeaderTimeout: 5 * time.Second,
        IdleTimeout:       60 * time.Second,
    }

    log.Fatal(server.ListenAndServe())
}
```

面试官可能继续问：

1. Go HTTP Server 如何处理并发请求？

对于 HTTP/1.x，`net/http` 通常为每个连接创建服务 goroutine，并在该连接内处理请求。

HTTP/2 则支持多个 Stream 并发处理，不应简单套用 HTTP/1.x 的连接处理模型。

2. 如何防止 Slowloris 类攻击？

应合理设置：

- `ReadHeaderTimeout`
- `ReadTimeout`
- `WriteTimeout`
- `MaxHeaderBytes`

并结合连接数限制、反向代理和流量防护策略。

3. 为什么 HTTP Client 应该复用？

因为复用 `http.Client` 及其底层 `Transport` 可以复用连接池，减少重复建立 TCP/TLS 连接的开销。

4. 为什么要关闭 Response Body？

因为及时读取并关闭响应体有助于释放相关资源，并在满足条件时让连接重新进入复用状态。

## 九、面试时的 90 秒参考答案

> HTTP 是应用层通信协议，HTTPS 通常是在 HTTP 和传输层之间引入 TLS，提供数据加密、完整性保护和服务端身份认证。
>
> HTTP/1.1 主要使用持久连接，HTTP/2 引入二进制分帧和多路复用，但仍存在 TCP 层的队头阻塞问题。HTTP/3 则基于 QUIC，使用 UDP 承载可靠传输并支持独立的 Stream。
>
> 对于 HTTPS，客户端首先建立传输连接，然后执行 TLS 握手。TLS 1.3 通常通过 ECDHE 协商密钥，并使用证书验证服务端身份，之后通过对称加密保护 HTTP 数据。
>
> WAF 要检查 HTTPS 的 HTTP 请求内容，通常需要位于 TLS 终止点或与其集成。WAF 解密之后进行 HTTP 解析、规则匹配和风险判断，再决定是否转发给后端。
>
> 在 WAF 系统开发中，我还会特别关注 HTTP 解析一致性、请求体边界、连接复用、超时管理以及 TLS 证书和密钥的安全管理。

## 十、二面高频题速查

# 3、Linux 服务器突然出现大量 TCP 连接超时，怎么排查？

### 标准回答

我会先确定连接超时发生在哪个阶段，再按照客户端、网络链路、服务器内核、应用程序四层进行排查。

TCP 连接超时通常可以分为三类：

| 现象                | 可能原因                                         |
| ------------------- | ------------------------------------------------ |
| TCP Connect Timeout | SYN 丢包、防火墙、路由异常、SYN 队列压力         |
| Connection Reset    | 收到 RST，可能是端口关闭、应用异常或中间设备重置 |
| Read Timeout        | 已建立连接，但应用处理慢、网络丢包或后端阻塞     |

其中，Connect Timeout 与 Read Timeout 不能混为一谈。

### 排查步骤

第一步：检查网络和 TCP 连接状态。

```
ss -s
ss -lnt
ss -ant state syn-recv
ss -ant state time-wait
```

`ss -s` 查看连接状态汇总；`ss -lnt` 可以观察监听端口的队列情况。

对于 LISTEN Socket，`Recv-Q` 通常表示当前已完成握手、等待应用接受的连接数，`Send-Q` 表示有效的监听 backlog 上限。

第二步：查看 TCP 错误统计。

```
nstat -az | grep -E 'Listen|Retrans|Timeout'
cat /proc/net/netstat
```

关注监听队列溢出、TCP 重传和超时计数。要比较故障发生前后的增量，而不是只看累计值。

第三步：抓包确定问题位置。

```
tcpdump -i any -nn 'tcp port 8080'
```

根据抓包结果判断：

- SYN 发出但没有 SYN-ACK：检查路径、防火墙及服务端。
- 收到 SYN-ACK 但握手未完成：检查客户端和返回路径。
- 握手完成但业务响应慢：检查应用队列、线程/Goroutine、数据库和网络传输。

第四步：检查应用和系统资源。

```
top
vmstat 1
sar -n TCP,ETCP 1
dmesg -T | tail -100
```

检查 CPU、内存、FD 耗尽、内核日志等问题。

### 面试官追问

Q：SYN Queue 和 Accept Queue 有什么区别？

TCP 服务端一般涉及两类队列：

- SYN Queue：管理尚未完成握手的连接请求，具体行为受 SYN Cookies 等机制影响。
- Accept Queue：保存已经完成握手、等待应用调用 `accept()` 的连接。

`tcp_max_syn_backlog` 主要控制未完成握手请求的队列上限，`somaxconn` 则限制应用 `listen(backlog)` 的有效 backlog 上限。

The Linux Kernel documentation+1



Q：大量 TIME_WAIT 一定是问题吗？

不是。TIME_WAIT 是 TCP 正常关闭连接的机制，用于处理延迟报文并避免旧连接影响后续连接。

真正要关注的是连接创建速率、临时端口占用、FD、内存和 conntrack 是否出现瓶颈。

面试加分点： 不要上来就说扩大 `somaxconn`。应先证明监听队列确实是瓶颈，否则只是掩盖问题。



# 4、Linux 收到 TCP 数据包后，从网卡到应用程序经历什么？

### 标准回答

以常见的 Linux 网络接收路径为例：

网卡 NIC

接收以太网帧，通过 DMA 写入内存

硬中断 IRQ

通知 CPU 有收包事件

NAPI / SoftIRQ

批量轮询并处理收包

网络协议栈

IP 层路由检查、TCP 连接识别等

Socket 接收缓冲区

将数据交给对应 Socket 管理

应用程序

通过 read / recv 等系统调用读取

需要强调：这是简化后的典型路径，实际路径可能受到 GRO、RPS、XDP、Netfilter、虚拟网卡等机制的影响。

### 面试官追问

Q：为什么 Linux 要使用 NAPI？

早期如果每收到一个数据包就触发一次中断，在高 PPS 场景下会产生大量中断开销。

NAPI 使用中断通知与批量轮询相结合的方式，减少中断压力，提高吞吐量。

Q：软中断处理不过来会怎样？

可能出现接收积压、丢包、网络延迟增加。部分软中断工作可能由 `ksoftirqd` 线程继续处理。

检查：

```
cat /proc/softirqs
cat /proc/net/softnet_stat
ethtool -S eth0
```

Q：eBPF 如何定位网络延迟？

可以在合适的内核函数或 Tracepoint 上挂载 eBPF 程序，采集时间戳、连接标识、丢包事件及调用信息。

例如使用 bpftrace 或 BCC 工具观察 TCP 重传、连接状态以及 Socket 行为。

关键是能够回答：数据包到达了哪里、在哪个阶段出现异常、是否存在明显的排队或处理延迟。
