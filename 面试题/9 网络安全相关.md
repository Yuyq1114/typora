# 1、SQL 注入原理与 WAF 检测机制



这道题是奇安信 WAF 控制面开发岗位的基础高频题。

面试官通常会从三个方向考察：

1. **攻击原理**：SQL 注入为什么发生？有哪些类型？
2. **防御原理**：参数化查询为什么能防止 SQL 注入？
3. **WAF 原理**：WAF 如何识别 SQL 注入？为什么存在绕过、误报和漏报？

对于你来说，第三部分尤其重要，因为你之前做过 HTTP 流量解析、敏感词匹配和 API 风险监测。

------

## 一、SQL 注入是什么？

SQL 注入（SQL Injection，SQLi）是指应用程序将不可信的用户输入直接拼接进 SQL 语句，导致输入内容被数据库解释为 SQL 语法的一部分。

例如：

```
username := r.FormValue("username")
password := r.FormValue("password")

query := "SELECT * FROM users WHERE username = '" +
    username + "' AND password = '" + password + "'"

rows, err := db.Query(query)
```

正常情况下，用户输入：

```
username = admin
password = 123456
```

最终执行：

```
SELECT * FROM users
WHERE username = 'admin'
AND password = '123456';
```

但是，如果攻击者能够控制输入，就可能通过特殊字符改变 SQL 原本的语义。

例如在用户名中输入：

```
admin' --
```

在支持 `--` 行注释的数据库及相应语法条件下，可能导致后面的密码条件被注释。

最终 SQL 的有效逻辑可能变成：

```
SELECT * FROM users
WHERE username = 'admin';
```

原本要求同时验证用户名和密码，现在可能只验证用户名。

**根本原因：应用程序没有正确区分 SQL 代码与用户数据。**

另外，真实登录系统不应该将明文密码直接作为 SQL 条件进行比较，而应使用安全的密码哈希与验证机制。

## 二、SQL 注入有哪些类型？

常见 SQL 注入可以分为以下几类。

| 类型         | 原理                               | 特征                   |
| ------------ | ---------------------------------- | ---------------------- |
| 联合查询注入 | 利用 UNION 组合查询结果            | 可能直接返回额外数据   |
| 报错注入     | 利用数据库错误信息泄露数据         | 依赖错误是否向外暴露   |
| 布尔盲注     | 通过真假条件观察响应差异           | 不需要直接返回数据     |
| 时间盲注     | 利用条件执行造成的时间差异         | 通过响应时间推断信息   |
| 带外注入     | 借助数据库外部通信能力传出信息     | 依赖数据库权限和环境   |
| 二次注入     | 恶意内容先被存储，之后进入动态 SQL | 注入发生在后续使用阶段 |

### 面试追问：什么是盲注？

假设一个存在 SQL 注入的接口不会返回查询结果，也不会直接显示 SQL 错误。

攻击者仍然可能通过响应差异判断某个条件是否成立。

例如：

```
条件成立 → 页面返回 A
条件不成立 → 页面返回 B
```

或者：

```
条件成立 → 响应明显变慢
条件不成立 → 正常响应
```

这分别对应布尔盲注和时间盲注的基本思想。

**需要理解：SQL 注入并不要求数据库直接返回查询结果。只要攻击者能够通过可观察行为获取信息，就可能构成漏洞利用。**

## 三、为什么参数化查询可以防止 SQL 注入？

这是最重要的防御措施之一。

错误做法：

```
query := "SELECT * FROM users WHERE username = '" +
    username + "'"

db.Query(query)
```

正确做法：

```
row := db.QueryRow(
    "SELECT id FROM users WHERE username = ?",
    username,
)
```

这里以 MySQL 风格的占位符为例。

PostgreSQL 常见写法：

```
row := db.QueryRow(
    "SELECT id FROM users WHERE username = $1",
    username,
)
```

### 参数化查询为什么安全？

因为 SQL 语句结构与参数值被分别处理。

概念上：

```
SQL 结构：
SELECT id FROM users WHERE username = ?

参数：
username = 用户输入
```

数据库驱动和数据库会按照参数绑定的语义处理输入，而不是把输入重新解释为 SQL 结构。

即使输入包含引号、注释符等特殊字符，也应该作为数据值处理。

### 面试追问：仅转义单引号可以吗？

不建议。

原因包括：

- 不同数据库的字符串语法不同。
- 字符编码和转义规则可能存在差异。
- 数字、标识符和其他 SQL 语法位置不一定使用单引号。
- 手动拼接容易遗漏特殊情况。

参数化查询才是处理 SQL 数据值的首选方式。

但注意：

**参数化查询通常不能直接参数化表名、列名和排序方向等 SQL 标识符或语法结构。**

例如，动态排序字段应该采用白名单：

```
allowedColumns := map[string]string{
    "name":       "name",
    "created_at": "created_at",
}

column, ok := allowedColumns[sortField]
if !ok {
    return errors.New("invalid sort field")
}

query := "SELECT * FROM users ORDER BY " + column
```

这里的安全性来自服务端固定的字段白名单，而不是用户输入本身。

## 九、面试官可能继续追问

| 追问                        | 回答重点                                |
| --------------------------- | --------------------------------------- |
| SQL 注入根本原因是什么？    | SQL 结构与用户输入未正确分离            |
| 参数化查询为什么安全？      | 数据值作为参数绑定，而不是拼接 SQL      |
| ORM 能否完全防止 SQL 注入？ | 不能，原生 SQL 拼接和动态标识符仍有风险 |
| WAF 能否完全防止 SQL 注入？ | 不能，无法替代应用层安全编码            |
| 为什么单纯使用正则不够？    | 上下文不足、编码差异、误报和漏报        |
| WAF 为什么需要规范化？      | 处理编码并降低解析语义不一致的风险      |
| 规则如何高性能匹配？        | 预编译、分层检测、多模式匹配            |
| 规则更新如何避免中断服务？  | 新版本预编译、校验、原子切换            |
| 500 个引擎如何同步规则？    | 持久化任务、版本号、重试、状态对账      |
| WAF 误拦截怎么办？          | 观察模式、灰度发布、规则例外和回滚      |
