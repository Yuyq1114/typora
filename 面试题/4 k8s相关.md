# 0、Kubernetes 核心组件有哪些？

### 标准回答

Kubernetes 主要由控制平面和工作节点两部分组成。

控制平面：

| 组件                     | 职责                                         |
| ------------------------ | -------------------------------------------- |
| API Server               | 提供集群 API，完成认证、鉴权、准入和资源操作 |
| etcd                     | 持久化保存 Kubernetes 集群状态               |
| Scheduler                | 给未绑定节点的 Pod 选择运行节点              |
| Controller Manager       | 运行各类控制器，协调实际状态与期望状态       |
| Cloud Controller Manager | 集成云厂商的节点、负载均衡等资源能力         |

工作节点：

| 组件                  | 职责                         |
| --------------------- | ---------------------------- |
| Kubelet               | 管理本节点的 Pod 生命周期    |
| Container Runtime     | 创建、启动和管理容器         |
| kube-proxy 或替代方案 | 实现 Kubernetes Service 转发 |
| CNI 实现              | 配置 Pod 网络并实现连通性    |



# 0.1 Kubernetes Service 如何转发流量？iptables、IPVS、eBPF 有什么区别？

### 标准回答

Service 为一组动态变化的后端 Endpoint 提供稳定的访问入口。

假设：

```
Service ClusterIP：10.43.0.10:80
Pod A：10.42.1.20:8080
Pod B：10.42.2.30:8080
```

客户端访问 `10.43.0.10:80`，内核中的 Service 数据路径将请求转发给某一个符合条件的后端 Endpoint。

在传统 kube-proxy iptables 模式中，核心实现是通过 Netfilter 规则进行 DNAT。

```
客户端 Pod
    ↓
访问 ClusterIP
    ↓
节点网络栈
    ↓
Netfilter 规则匹配 Service
    ↓
DNAT：ClusterIP → Pod IP
    ↓
通过路由和 CNI 数据路径发送
    ↓
目标 Pod
```

具体 Hook 和 NAT 行为取决于流量来源、代理实现等条件。

### 追问：为什么 ClusterIP 通常看不到实体网卡？

因为 ClusterIP 是逻辑服务地址，不要求绑定在物理网卡上。

传统模式通过内核规则识别目标 Service IP，并把流量转发到真实后端。

需要区分：在某些 IPVS 实现中，可能会把 Service IP 配置到 `kube-ipvs0` 这样的 Dummy Interface 上。

### 追问：iptables 与 IPVS 的区别？

| 对比            | iptables                   | IPVS                       |
| --------------- | -------------------------- | -------------------------- |
| 核心机制        | Netfilter 规则链           | 内核虚拟服务与连接调度     |
| 负载均衡        | 通过规则选择后端           | 轮询、加权、最少连接等     |
| 规则规模        | 大规模规则可能增加维护成本 | 通过虚拟服务与后端结构管理 |
| Kubernetes 状态 | 长期使用                   | 已被弃用                   |

重要版本变化： Kubernetes 从 v1.35 起弃用了 kube-proxy 的 IPVS 模式，官方现在推荐在满足条件的环境中考虑 nftables 模式作为替代。IPVS 仍值得学习，因为现有生产环境可能继续使用它。

Kubernetes+1



### 追问：kube-proxy 能完全被替代吗？

可以。

例如部分 Cilium 配置可以利用 eBPF 实现 Service 负载均衡，不必使用传统 kube-proxy 数据路径。

不过 CNI 和 Service 代理不是同一个概念：

- CNI 主要负责 Pod 网络配置及网络连通性。
- Service 代理负责 Service 到后端 Endpoint 的流量转发。

两种能力可以由同一个网络方案实现，但逻辑职责不同。



# 0.2  Pod A 跨 Node 访问 Pod B，网络全过程是什么？

### 标准回答

假设 Pod A 在 Node 1，Pod B 在 Node 2，使用 Flannel VXLAN 网络。

Node 1

Pod A：10.42.1.10

veth → 主机路由

VXLAN 封装

Node 2

Pod B：10.42.2.10

主机路由 → veth

VXLAN 解封装

节点 Underlay 网络

Node IP → UDP/VXLAN → Node IP

具体过程：

1. Pod A 通过自己的网卡发送数据包。
2. 数据包经过 veth pair 进入 Node 1 网络栈。
3. Node 1 根据路由表判断目标 Pod 在其他节点。
4. Flannel VXLAN 数据路径将原始数据包封装到外层 UDP/IP 报文。
5. Underlay 网络把封装后的数据发送到 Node 2。
6. Node 2 解封装后通过本地路由和 veth 交给 Pod B。

这是 Flannel VXLAN 的典型路径，其他 CNI 不一定这样实现。

### 追问：Flannel 和 Calico 有什么区别？

Flannel 的定位更偏基础 Pod 网络连通性；Calico 除了网络连接，还提供网络策略等能力。

典型实现区别：

- Flannel VXLAN：通过 Overlay 封装跨节点流量。
- Calico BGP：可通过路由分发 Pod 网段，不必依赖 VXLAN。
- Calico 也支持 VXLAN 等其他数据路径，因此不能简单说 Calico 一定使用 BGP。

### 追问：跨节点 Pod 无法通信，怎么排查？

先按路径逐层缩小范围：

```
# 查看 Pod 和节点位置
kubectl get pod -A -o wide

# 查看节点网络
ip addr
ip route

# 查看 CNI 组件
kubectl get pods -n kube-system

# 查看节点网卡及隧道接口
ip -d link

# 检查防火墙和转发规则
iptables -S
nft list ruleset
```

重点判断：

- Pod 到本机网关是否通？
- Pod 访问同节点 Pod 是否正常？
- Node IP 之间是否可达？
- 跨节点 Pod IP 是否可达？
- 使用 VXLAN 时，节点 UDP 4789 等实际配置的端口是否放通？
- CNI 是否成功建立路由、隧道和转发规则？
- NetworkPolicy 是否拒绝流量？

加分点： 先区分 Pod IP 访问故障与 Service IP 访问故障。如果 Pod IP 正常而 Service IP 不通，应优先检查 Service、EndpointSlice 和代理数据路径。

# 0.3 CRI、containerd、runc、OCI 的关系是什么？

### 标准回答

它们位于不同抽象层：

Kubelet

负责 Kubernetes Pod 生命周期

CRI 接口

Kubelet 与容器运行时的通信规范

containerd

实现容器运行时服务和镜像、容器管理

runc

常见的 OCI 容器运行时实现

Linux Kernel

Namespace、Cgroups、安全隔离等

需要注意 OCI 是标准体系，不是独立进程。上图是逻辑调用关系，containerd 实际通过 shim 等组件管理容器进程。

### 面试官追问

Q：Kubelet 如何创建容器？

典型 CRI 调用流程包括：

```
RunPodSandbox
      ↓
CreateContainer
      ↓
StartContainer
```

Pod Sandbox 主要提供 Pod 级别的运行环境，包括共享网络命名空间等。

在常见 Linux 实现中，可以通过一个 Pause 容器维护 Pod 网络命名空间，但并不是说所有容器架构都必须完全采用同一实现。

Q：什么是 OCI？

OCI 包含镜像格式和运行时规范等标准。它规定容器镜像、运行配置等应该遵循的约定，允许不同实现互操作。

Q：为什么 Kubernetes 不直接调用 Docker CLI？

因为 Kubernetes 希望通过统一 CRI 对接不同容器运行时，降低对单个容器引擎的依赖。



# 0.4  Pod 长期处于 Pending，怎么排查？

### 标准回答

我会先查看 Pod Events，因为 Scheduler 无法调度时通常会给出较明确的原因。

```
kubectl get pod -A -o wide
kubectl describe pod <pod-name> -n <namespace>
kubectl get events -A --sort-by=.lastTimestamp
```

### 常见原因

| 原因                 | 检查内容                            |
| -------------------- | ----------------------------------- |
| CPU / 内存不足       | Requests 与 Node Allocatable        |
| Taint 不匹配         | Taints 和 Tolerations               |
| Node Affinity 不匹配 | 节点标签和亲和性                    |
| PVC 未绑定           | StorageClass、PVC、PV、拓扑         |
| 节点状态异常         | Ready、DiskPressure、MemoryPressure |
| 资源拓扑限制         | Pod Anti-Affinity、TopologySpread   |

### 追问：Scheduler 的工作流程是什么？

可以概括为：

过滤（Filter）→ 评分（Score）→ 选择节点 → 绑定（Bind）。

Filter 阶段淘汰不符合硬性约束的节点。

Score 阶段对剩余节点打分。

之后通过绑定操作确定目标节点。

### 追问：PVC 没绑定就一定无法调度吗？

不一定。

例如 `WaitForFirstConsumer` 类型的 StorageClass，会等到有消费它的 Pod 后，结合节点拓扑进行存储供应或绑定。

所以不能简单地把 Pending 一律归因于 PVC 异常。需要结合 StorageClass 的 `volumeBindingMode` 和 Pod Events 判断。



# 0.5 Kubernetes 出现大量 OOMKilled，怎么排查？

### 标准回答

首先确认是否真的发生了 OOM Kill，而不是看到退出码 137 就直接下结论。

```
kubectl describe pod <pod> -n <ns>

kubectl get pod <pod> -n <ns> \
  -o jsonpath='{.status.containerStatuses[*].lastState}'
```

重点检查 `lastState.terminated.reason`、退出码和时间。

### 排查步骤

第一步：确认内存限制与历史使用趋势。

```
kubectl top pod -n <ns> --containers
kubectl describe pod <pod> -n <ns>
```

同时查看 Prometheus 中容器工作集、内存 Limit、OOM 事件等历史指标。

注意 `kubectl top` 只能反映当前或近期用量，无法代替历史分析。

第二步：检查 Go 应用是否存在内存问题。

如果是 Go 服务，可以使用 pprof：

```
go tool pprof http://host:6060/debug/pprof/heap
```

重点关注：

- `inuse_space`。
- `alloc_space`。
- 对象数量。
- 内存分配热点。
- Goroutine 数量。
- GC 频率与停顿。

第三步：区分内存泄漏和正常内存增长。

例如：

- 缓存没有上限。
- Channel 积压大量任务。
- Goroutine 泄漏。
- 大批量数据一次性加载。
- 内存映射、Cgo 或内核相关内存增长。

并非所有 RSS 增长都能直接在 Go Heap Profile 中找到。

### 面试官追问

Q：退出码 137 一定是 OOMKilled 吗？

不一定。

137 通常表示进程被 SIGKILL 终止。

OOM Killer 可以导致 SIGKILL，但手动 `kill -9`、某些强制终止场景也可能产生相同退出码。

Q：如何提前预防？

- 根据实际工作集设置 Requests/Limits。
- 给缓存、队列、并发和批量任务设置上限。
- 设置内存增长趋势告警。
- 对 Go 服务合理使用 GC 与内存限制相关设置。
- 定期进行长时间压测。
- 避免无限重试造成内存积压。





# 1、Kubernetes 如何管理 GPU？



这是 AI Infra 工程师非常核心的一道面试题，尤其适合从 Go/Kubernetes 平台开发转型的工程师。

面试官：

> Kubernetes 原生主要管理 CPU 和内存，那么它是如何发现、调度和分配 NVIDIA GPU 的？请介绍 Device Plugin 的工作原理，以及从 Pod 创建到容器使用 GPU 的完整流程。

## 一、首先理解 GPU 为什么需要 Device Plugin

Kubernetes 原生支持 CPU、Memory 等基础资源。

例如：

```
resources:
  requests:
    cpu: "2"
    memory: "4Gi"
  limits:
    cpu: "4"
    memory: "8Gi"
```

但 GPU 属于硬件加速设备，存在不同厂商、驱动和设备分配方式。

Kubernetes 不可能在核心代码中实现所有硬件设备的具体管理逻辑。

因此，它提供了 Device Plugin Framework，让硬件厂商通过插件向 Kubelet 注册并管理设备。

对于 NVIDIA GPU，常见方案是使用 NVIDIA Device Plugin。

## 二、Device Plugin 的完整工作流程

简化流程。实际 Pod 创建后，Scheduler 根据已公布的资源选择节点，随后 Kubelet 执行设备分配与容器启动。

### 第一步：Device Plugin 发现 GPU

Device Plugin 通常通过 DaemonSet 部署在 GPU 节点上。

它与 NVIDIA 驱动及相关设备管理库交互，发现 GPU 的数量、设备 ID、健康状态等信息。

例如节点上有 4 张 GPU。

### 第二步：向 Kubelet 注册资源

Device Plugin 通过 Unix Domain Socket 使用 gRPC 向 Kubelet 注册。

注册的资源名称通常是：

```
nvidia.com/gpu
```

注册完成后，Kubelet 会通过 Device Plugin API 进行设备枚举和健康状态更新。

Device Plugin 的典型接口包括：

| 接口                     | 作用                             |
| ------------------------ | -------------------------------- |
| `Register`               | 向 Kubelet 注册设备插件          |
| `ListAndWatch`           | 提供设备列表及健康状态变化       |
| `Allocate`               | 为容器分配指定设备并返回运行配置 |
| `GetPreferredAllocation` | 可选，辅助选择设备组合           |
| `PreStartContainer`      | 可选，容器启动前的设备准备       |

其中，`ListAndWatch` 和 `Allocate` 尤其重要。

### 第三步：Node 上报 GPU 资源

Kubelet 将资源信息更新到 Node Status。

例如：

```
status:
  capacity:
    nvidia.com/gpu: "4"
  allocatable:
    nvidia.com/gpu: "4"
```

可以执行：

```
kubectl describe node gpu-node-01
```

查看 GPU 资源。

如果没有 `nvidia.com/gpu`，需要检查驱动、Device Plugin、Kubelet 日志和插件注册情况。

注意：安装 NVIDIA 驱动本身不意味着 Kubernetes 一定会自动识别 GPU 扩展资源。

## 三、Scheduler 如何调度 GPU？

假设用户提交：

```
apiVersion: v1
kind: Pod
metadata:
  name: gpu-test
spec:
  containers:
    - name: cuda
      image: nvidia/cuda:12.6.3-base-ubuntu24.04
      command: ["sleep", "3600"]
      resources:
        limits:
          nvidia.com/gpu: 2
```

Scheduler 需要寻找能够满足两张 GPU 资源请求的节点。

假设集群状态：

| Node   | 可分配 GPU 资源 | 已请求 GPU | 剩余 |
| ------ | --------------- | ---------- | ---- |
| Node A | 4               | 3          | 1    |
| Node B | 8               | 4          | 4    |
| Node C | 2               | 2          | 0    |

从 GPU 资源数量角度看，Node B 可以满足 Pod 的请求。

但最终还需要满足 CPU、内存、污点容忍、亲和性等其他调度条件。

### 追问：Scheduler 会选择具体 GPU 编号吗？

默认情况下，不会。

Scheduler 主要决定 Pod 应该调度到哪个 Node。

具体分配哪几张 GPU，一般由目标节点的 Kubelet 结合 Device Plugin 完成。

这是 AI Infra 面试非常重要的区分：

- Scheduler：节点选择。
- Kubelet / Device Manager：节点内设备分配。
- Device Plugin：提供设备信息和分配配置。
- Container Runtime：根据配置启动可以访问相应 GPU 的容器。

## 四、Allocate 接口究竟做什么？

这是我作为面试官会重点追问的问题。

> 如果 Pod 请求两张 GPU，Device Plugin 的 Allocate 是怎么工作的？

当 Kubelet 为容器选定具体设备后，会调用 Device Plugin 的 `Allocate` 接口。

插件返回容器运行所需的设备分配信息，例如：

- 设备标识。
- 环境变量。
- Device Nodes。
- Mounts。
- CDI 设备引用等。

具体取决于插件版本与配置方式。

然后由 Kubelet 和容器运行时配合，将必要的设备访问能力注入容器。

面试重点：Allocate 不负责选择 Kubernetes Node，它负责配合 Kubelet 完成节点内设备分配。

## 五、GPU 为什么不能直接像 CPU 一样分配 0.5 张？

因为 Kubernetes 中传统 GPU 扩展资源的默认语义通常是整数个设备。

例如：

```
limits:
  nvidia.com/gpu: 1
```

但不能默认写：

```
limits:
  nvidia.com/gpu: 0.5
```

来获得半张物理 GPU。

原因在于 GPU 的计算资源、显存、上下文和隔离机制，并不像 CPU 时间片那样可以通过普通 cgroup CPU 配额直接统一管理。

不过，这不意味着 GPU 完全不能共享。

常见方法包括：

| 方法           | 作用                            | 特点                       |
| -------------- | ------------------------------- | -------------------------- |
| Time-Slicing   | 多个任务分时使用 GPU            | 简单，但显存与故障隔离有限 |
| NVIDIA MPS     | 多 CUDA 进程共享 GPU 计算资源   | 需考虑隔离与兼容性         |
| MIG            | 将支持的 GPU 划分成硬件隔离实例 | 隔离相对更明确             |
| vGPU           | GPU 虚拟化                      | 依赖硬件、驱动和授权体系   |
| 自定义共享调度 | 平台自定义分配规则              | 需自行处理资源核算和隔离   |

### MIG 是什么？

MIG（Multi-Instance GPU）允许支持该功能的 NVIDIA GPU 划分成多个独立 GPU 实例。

例如一张支持 MIG 的 GPU，可以划分成多个具备特定计算和显存资源的实例。

但 MIG 不是所有 NVIDIA GPU 都支持的功能，也不能假设所有显卡都可以划分成相同的份额。

你本地的 RTX 4070 Super 不属于常见支持 MIG 的数据中心 GPU，因此不能在本机用它验证真实 MIG 分区。

## 六、GPU 调度最大的难点是什么？

普通资源调度通常主要考虑资源数量。

GPU 调度还需要考虑设备拓扑、显存容量、共享情况和通信成本。

例如某个模型需要 4 张 GPU。

如果一个节点有 8 张 GPU，其中部分 GPU 通过高速 NVLink 互联，而其他设备之间主要通过 PCIe 通信，那么不同 GPU 组合的通信性能可能不同。

这就需要考虑 GPU Topology Awareness。

还可能涉及：

- NUMA 亲和性。
- PCIe 拓扑。
- NVLink / NVSwitch。
- GPU 型号与显存容量。
- GPU 碎片化。
- 多租户隔离。
- Gang Scheduling。
- GPU 抢占和任务优先级。

### 什么是 GPU 碎片化？

例如有两个节点：

```
Node A：剩余 2 张 GPU
Node B：剩余 2 张 GPU
```

集群总共剩余 4 张 GPU。

但如果某个 Pod 要求同一节点上有 4 张 GPU，就无法调度。

这属于资源碎片化的一种表现。

即使集群整体剩余资源充足，也不意味着每个任务都能够成功调度。

## 七、Gang Scheduling 是什么？

假设一个分布式训练任务需要 4 个 Worker Pod，每个 Pod 使用 2 张 GPU。

也就是说整个任务需要 8 张 GPU。

普通调度可能出现：

```
Worker 1：Running
Worker 2：Running
Worker 3：Pending
Worker 4：Pending
```

前两个 Worker 已经占用了 GPU，但整个分布式训练任务仍然无法开始。

Gang Scheduling 希望将有关联的一组 Pod 作为整体考虑，只有满足一定的组调度条件后才允许执行。

可以通过 Volcano、Kueue 与适配的调度机制等技术体系解决不同层次的队列管理和协同调度问题，但二者的职责并不完全相同。

## 八、实际工程题：GPU 节点故障怎么办？

假设一个 vLLM 推理 Pod 正运行在 Node A，Node A 突然宕机。

可能发生：

1. Node Controller 检测节点心跳异常。
2. Node 被标记为 NotReady 或 Unknown。
3. 满足驱逐条件后，工作负载控制器在其他节点创建替代 Pod。
4. Scheduler 为替代 Pod 分配新的可用节点。
5. Kubelet 准备 GPU 并启动容器。
6. 模型权重加载到 GPU。
7. 推理服务完成 Readiness 检查。
8. 新实例开始接收请求。

但需要注意：

正在进行中的推理请求通常会中断，不能认为 Kubernetes 自动实现了请求级的无损迁移。

如果想降低影响，还需要：

- 多副本推理服务。
- 服务端请求路由与健康检查。
- 请求重试策略。
- 模型预加载或预热。
- 必要时进行请求状态恢复。

模型越大，重新加载的时间可能越长，因此 GPU 故障恢复不只是调度问题，还涉及模型加载成本和服务可用性设计。

## 九、面试时的 90 秒参考答案

> Kubernetes 原生主要管理 CPU、内存等标准资源，对于 GPU 等特殊硬件，通过 Device Plugin Framework 进行扩展。
>
> NVIDIA Device Plugin 通常运行在 GPU 节点上，通过 gRPC 向 Kubelet 注册 `nvidia.com/gpu` 资源，并通过 ListAndWatch 上报设备及健康状态。
>
> Kubelet 再将可分配 GPU 数量更新到 Node Status。
>
> 当 Pod 请求 GPU 时，Scheduler 根据节点的扩展资源及其他调度条件选择 Node，但通常不负责选择具体 GPU 编号。
>
> Pod 调度到目标节点后，Kubelet 负责节点内设备分配，并通过 Device Plugin 的 Allocate 接口取得容器运行所需的设备配置，再由容器运行时完成设备接入。
>
> 对于复杂的 AI Infra，还需要考虑 GPU 共享、MIG、设备拓扑、NUMA、资源碎片化以及 Gang Scheduling。
>
> 如果要设计生产级 GPU 平台，我还会重点考虑设备健康、节点故障恢复、模型加载时间、资源利用率和多租户隔离。

# 2、Pod 从创建到 Running，完整经历了什么？



面试官：

> 用户执行 `kubectl apply -f pod.yaml` 后，Kubernetes 内部发生了哪些事情？API Server、etcd、Scheduler、Kubelet、CRI、CNI、CSI 分别起什么作用？

## 一、整体流程

简化主流程。Scheduler、Kubelet 实际通过 API Server 观察和更新状态，并非直接顺序调用；Running 也不等于 Ready。

### 1. kubectl 向 API Server 发送请求

`kubectl apply` 将资源配置提交到 API Server。

API Server 进行：

- Authentication：认证用户身份。
- Authorization：校验 RBAC 等权限。
- Admission：执行准入控制。
- Validation：校验资源字段。
- Persistence：将资源状态持久化到 etcd。

如果创建的是 Deployment，API Server 首先保存 Deployment，后续由 Deployment Controller 创建 ReplicaSet，再由 ReplicaSet Controller 创建 Pod。

### 2. Scheduler 选择 Node

新创建的普通 Pod 如果还没有 `spec.nodeName`，通常需要由 Scheduler 选择节点。

Scheduler 使用调度框架处理：

```
Scheduling Cycle
      │
      ▼
PreFilter
      │
      ▼
Filter
      │
      ▼
PostFilter（必要时）
      │
      ▼
PreScore
      │
      ▼
Score
      │
      ▼
Reserve
      │
      ▼
Permit
      │
      ▼
PreBind
      │
      ▼
Bind
      │
      ▼
PostBind
```

其中：

- Filter：哪些 Node 可以运行这个 Pod？
- Score：在可用 Node 中，哪个更合适？
- Bind：将 Pod 与选定的 Node 关联。

### 3. Kubelet 观察到分配给自己的 Pod

每个 Node 上运行 Kubelet。

Kubelet 通过 API Server 获得与本节点相关的 Pod 期望状态，然后负责将其落实到实际运行环境。

主要工作：

- 准备存储卷。
- 创建 Pod Sandbox。
- 协调容器网络设置。
- 拉取镜像。
- 创建和启动容器。
- 执行健康探针。
- 更新 Pod Status。

这里要特别强调：

Kubelet 并不直接负责 Kubernetes 全局调度，它负责节点本地的 Pod 生命周期。

### 4. CRI、CNI、CSI 分别负责什么？

| 接口 | 全称                        | 职责                      |
| ---- | --------------------------- | ------------------------- |
| CRI  | Container Runtime Interface | Kubelet 与容器运行时交互  |
| CNI  | Container Network Interface | 为容器配置网络            |
| CSI  | Container Storage Interface | 将存储系统接入 Kubernetes |

举例：

```
Kubelet
   │
   ├── CRI → containerd → 启动容器
   │
   ├── CNI → 配置 Pod 网络
   │
   └── CSI → 挂载持久化存储
```

严格来说，CNI 通常由容器运行时在创建 Sandbox 时调用相应网络插件；CSI 则通过 Kubelet 的卷管理流程及相关 CSI 组件参与卷挂载。

不是 Kubelet 直接调用三个完全相同形式的接口。

## 二、Running 和 Ready 有什么区别？

这也是面试官可能深入追问的地方。

Running： Pod 已经绑定到节点，至少一个容器正在运行、启动或重启。

Ready： Pod 满足相关就绪条件，可以作为合适的服务后端。

假设一个大模型推理容器：

```
Pod Running
     │
     ▼
Python 进程启动
     │
     ▼
加载模型权重
     │
     ▼
初始化 GPU 显存
     │
     ▼
推理引擎预热
     │
     ▼
Readiness Probe 成功
     │
     ▼
Pod Ready
```

大模型加载可能需要较长时间，因此 Running 并不能代表推理服务已经能够接收请求。

### AI Infra 中的实际问题

如果推理服务在启动后需要两分钟加载模型，不能因为容器进程启动成功就立即把请求路由过去。

应该合理设计：

- Startup Probe：为较慢的启动提供时间。
- Readiness Probe：判断是否可以接收请求。
- Liveness Probe：判断是否需要重启容器。

错误的探针配置可能导致模型尚未加载完成，就被 Kubernetes 反复重启。

## 三、如果 Pod 一直 Pending，如何排查？

优先执行：

```
kubectl describe pod <pod-name> -n <namespace>
```

重点查看 Events。

可能原因：

| 现象                        | 原因                     |
| --------------------------- | ------------------------ |
| Insufficient cpu            | CPU 资源不足             |
| Insufficient memory         | 内存资源不足             |
| Insufficient nvidia.com/gpu | GPU 扩展资源不足         |
| Untolerated taint           | Pod 不容忍 Node 污点     |
| Node affinity mismatch      | 节点亲和性不匹配         |
| PVC 尚未绑定                | 存储相关条件尚未满足     |
| 调度器或准入异常            | 相关控制链路无法正常工作 |

如果 Pod 已绑定节点但容器无法启动，还需要区分 ImagePullBackOff、CreateContainerConfigError、ContainerCreating 等状态及具体原因。

## 四、90 秒面试参考答案

> 当用户通过 kubectl 创建 Pod 时，请求首先到达 API Server，经过认证、授权、准入和校验后持久化到 etcd。
>
> Scheduler 通过 Watch 发现尚未绑定节点的 Pod，执行 Filter、Score 等调度流程，并通过 Bind 将 Pod 绑定到合适的 Node。
>
> 目标 Node 上的 Kubelet 获取 Pod 期望状态，协调存储、网络和容器运行时完成 Pod 启动。Kubelet 通过 CRI 与 containerd 等运行时通信，CNI 负责网络配置，CSI 负责存储接入。
>
> 容器启动后，Kubelet 持续检查状态和探针，并将 Pod Status 更新到 API Server。
>
> 对于 AI Infra，我会特别关注 GPU Device Plugin、模型加载时间及 Readiness。因为 Pod Running 不代表模型已经加载完成，更不代表推理服务已经可用。

## 五、深入追问

Q1：Scheduler 是否直接创建容器？

不是。Scheduler 只负责节点选择和绑定，容器由目标节点上的 Kubelet 协调启动。

Q2：如果 Scheduler 挂了，已经运行的 Pod 会停止吗？

不会。已经运行的 Pod 通常继续由 Kubelet 管理，但新的待调度 Pod 可能无法完成调度。

Q3：如果 API Server 挂了，现有容器会立即停止吗？

通常不会。节点上的现有容器可以继续运行，但集群的状态更新、管理和故障协调能力会受到影响。

Q4：Kubelet 如何知道 Pod 有变化？

Kubelet 通过 API Server 的 List/Watch 等机制获得变化，再通过本地同步流程将实际状态向期望状态推进。

# 3、Kubernetes Scheduler 调度原理



面试官：

> Kubernetes Scheduler 是如何将一个 Pod 调度到合适的 Node 上的？Filter、Score、Bind 分别做什么？如果要实现一个 GPU 感知调度器，你会如何设计？

这道题属于 AI Infra 面试的核心题目。对于你之前学习过的 Mini Scheduler，重点是把调度流程、Scheduler Framework 和真实的 GPU 调度需求串起来。

## 一、Scheduler 的核心职责

Kubernetes Scheduler 的职责是：

为尚未分配节点的 Pod 选择合适的 Node，并将调度结果提交给 API Server。

它本身不负责启动容器。

调度问题可以分为两个层次：

- Filter： 哪些 Node 满足 Pod 的硬性要求？
- Score： 在满足条件的 Node 中，哪个 Node 更合适？

例如，一个 Pod 需要：

```
resources:
  requests:
    cpu: "4"
    memory: "8Gi"
  limits:
    nvidia.com/gpu: 2
```

集群节点资源如下：

| Node   | 剩余 CPU | 剩余内存 | 剩余 GPU | 是否满足 |
| ------ | -------- | -------- | -------- | -------- |
| Node A | 8 核     | 16 GiB   | 1        | 否       |
| Node B | 12 核    | 32 GiB   | 4        | 是       |
| Node C | 6 核     | 16 GiB   | 2        | 是       |
| Node D | 16 核    | 64 GiB   | 0        | 否       |

Filter 后仅剩 Node B、Node C。

Score 可以进一步考虑资源利用率、GPU 拓扑、节点负载等因素。

最终假设选择 Node C，Scheduler 将 Pod 绑定到 Node C。

需要注意，Scheduler 依据的是 Kubernetes 资源请求和调度缓存中的资源占用，而不是简单读取实时 CPU/GPU 使用率。

## 二、Scheduler Framework 的完整流程

Scheduler Framework 的扩展点：

| 扩展点     | 核心作用                       |
| ---------- | ------------------------------ |
| QueueSort  | 决定 Pod 的排序顺序            |
| PreFilter  | 预计算资源、亲和性等信息       |
| Filter     | 排除不满足要求的 Node          |
| PostFilter | Filter 无可用节点时尝试补救    |
| PreScore   | 为评分阶段准备数据             |
| Score      | 给候选 Node 打分               |
| Reserve    | 在调度缓存或插件状态中预留资源 |
| Permit     | 允许、拒绝或等待绑定           |
| PreBind    | 执行绑定前的准备工作           |
| Bind       | 将 Pod 与 Node 绑定            |
| PostBind   | 绑定后的通知或清理工作         |

其中，调度分为两个主要周期：

Scheduling Cycle：选出目标 Node，通常串行执行。

Binding Cycle：执行绑定相关逻辑，不同 Pod 的绑定周期可以并发。

`Reserve` 阶段发生在绑定前，这有助于避免调度器因为 API Server 状态尚未更新而错误重复分配资源。

## 三、Filter 阶段具体检查什么？

在 Kubernetes 中，Filter 由多个插件执行。

几个最重要的插件如下。

### 1. NodeResourcesFit

检查节点资源是否足够：

```
Pod 请求 CPU 4 核
Node 剩余可调度 CPU 2 核

结果：Filter 失败
```

GPU 也可以作为扩展资源参与此类资源数量检查。

### 2. NodeAffinity

检查 Pod 对 Node Label 的选择条件。

例如：

```
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
        - matchExpressions:
            - key: accelerator
              operator: In
              values:
                - nvidia-a100
```

这个 Pod 只能被调度到满足标签条件的节点。

### 3. TaintToleration

节点可以通过 Taint 限制普通工作负载进入。

例如：

```
kubectl taint nodes gpu-node-01 \
  dedicated=gpu:NoSchedule
```

GPU Pod 需要相应的 Toleration 才能被调度过去。

### 4. PodTopologySpread

帮助控制 Pod 在节点、可用区等拓扑域上的分布。

例如为了高可用，避免全部推理副本集中在同一台 GPU 服务器上。

## 四、Score 阶段如何给 Node 打分？

Filter 的结果是可行或不可行。

Score 则在候选节点中进行优先级排序。

例如：

| Node   | CPU 得分 | GPU 拓扑得分 | 资源均衡得分 | 总分 |
| ------ | -------- | ------------ | ------------ | ---- |
| Node B | 70       | 90           | 60           | 220  |
| Node C | 85       | 60           | 90           | 235  |

在这个纯示例中，如果三个分数权重相同，Node C 总分最高。

真实 Scheduler 中，不同 Score 插件可以有不同权重，插件的原始得分通常会经过规范化或由框架按规定范围处理。

调度器最终根据加权得分选择 Node。

### GPU 调度应该如何打分？

这取决于业务目标。

目标 A：提高 GPU 利用率

可以优先选择已经分配了一部分 GPU、但仍然满足要求的节点，以便尽可能把负载集中起来。

这有利于释放其他节点用于大任务或节能。

目标 B：提高可用性

可以尽量让同一个模型的副本分布在不同节点、故障域中。

目标 C：提高多 GPU 通信性能

优先选择满足 GPU 拓扑要求的节点，例如具有高带宽 GPU 互联的设备组合。

这些目标可能冲突，所以不存在适用于所有 AI 任务的统一最优评分算法。

## 五、Scheduler 如何避免两个 Pod 抢占同一份 GPU 资源？

这是非常有价值的追问。

假设某个 Node 仅剩 2 张 GPU。

现在两个 Pod 同时请求：

```
Pod A：2 GPU
Pod B：2 GPU
```

如果两个调度操作都只读取同一份旧状态，就可能都认为资源充足。

Kubernetes Scheduler 通过内部调度缓存、节点资源请求核算、Assumed Pod 机制以及 Reserve/Unreserve 等流程管理调度中的资源占用。

简化理解：

```
节点剩余 GPU：2
      │
      ▼
调度 Pod A
      │
      ▼
缓存中预占 GPU：2
      │
      ▼
调度 Pod B
      │
      ▼
可用 GPU：0
      │
      ▼
Pod B 无法继续调度到该节点
```

但需要注意：

Scheduler 保证的是它管理的资源请求和调度缓存中的一致性，不代表能够完全防止所有形式的 GPU 超分配。

例如，第三方 GPU Sharing 插件自行维护的资源账本如果不正确，仍可能出现冲突。

另外，如果多个独立 Scheduler 同时管理同一种扩展资源，也需要设计明确的协调与资源所有权机制。

## 六、如果自己写 GPU Scheduler，应该怎么做？

面试官可能问：

> 现有 Scheduler 只认识 `nvidia.com/gpu` 数量，但你想根据显存容量、GPU 型号、NVLink 拓扑调度模型，应该怎么实现？

我会先区分：

需求一：按 GPU 类型调度。

可以通过 Node Label、Node Affinity 等方式实现。

例如：

```
nodeSelector:
  gpu-type: nvidia-a100
```

需求二：按 GPU 数量调度。

使用 Kubernetes 扩展资源：

```
resources:
  limits:
    nvidia.com/gpu: 4
```

需求三：按动态显存、GPU 拓扑和设备共享情况调度。

这时常规资源数量调度可能不足，需要扩展。

可以考虑：

- Scheduler Framework 自定义 Filter/Score 插件。
- Device Plugin 及设备资源管理机制。
- Dynamic Resource Allocation（DRA）。
- 外部 GPU 状态监控与调度缓存。
- 专用 GPU 调度平台。

现代 Kubernetes 的 DRA 能够表达比传统标量扩展资源更丰富的设备请求，但具体功能取决于集群版本、驱动及相关组件支持情况。

### 一个自定义 GPU Filter 的设计思路

假设模型要求：

```
gpu:
  count: 2
  minMemoryGiB: 40
  topology: nvlink
```

那么自定义 Filter 可以检查：

1. Node 是否有满足条件的 GPU。
2. GPU 显存容量是否足够。
3. 所需设备是否满足拓扑条件。
4. 设备是否已被其他任务分配。
5. 是否满足租户资源配额。

需要特别注意，Scheduler Framework 的常规 Filter 插件主要负责判断 Node 是否可行，并不会自动代替 Kubelet 选择具体的 GPU 设备。

如果调度决策依赖具体设备组合，还需要与节点侧设备分配机制协调，防止调度时选择的设备与最终实际分配的设备不一致。

## 七、AI Infra 专项追问：什么是 GPU 碎片化？

假设集群中有两台服务器：

```
Node A：剩余 GPU 2 张
Node B：剩余 GPU 2 张

集群总剩余：4 张
```

一个 Pod 请求 4 张 GPU：

```
resources:
  limits:
    nvidia.com/gpu: 4
```

虽然集群总共有 4 张空闲 GPU，但这个 Pod 无法被调度。

因为标准 Pod 的资源请求需要由一个 Node 满足。

这属于 GPU 资源碎片化。

可以通过以下方式改善：

- 合理设置 GPU 工作负载调度策略。
- 对大 GPU 任务进行资源预留。
- 使用队列和优先级管理。
- 在设备与隔离能力支持的情况下使用 GPU Sharing 或 MIG。
- 对分布式训练任务使用合适的多 Pod 调度协调。

但不能简单通过修改 Scheduler 就让一个普通 Pod 跨多个 Node 直接获得 4 张 GPU。

## 八、面试时的 90 秒参考答案

> Kubernetes Scheduler 负责给尚未绑定节点的 Pod 选择合适的 Node。
>
> 调度过程主要分为 Scheduling Cycle 和 Binding Cycle。在 Scheduling Cycle 中，Scheduler 先通过 PreFilter 和 Filter 筛选符合资源、亲和性、污点容忍等要求的 Node，然后通过 PreScore 和 Score 对候选节点评分。
>
> 选择节点后，会通过 Reserve、Permit 等扩展点进行资源预留和相关检查，随后在 Binding Cycle 中完成 PreBind、Bind、PostBind。
>
> Scheduler Framework 提供了可扩展的插件机制，可以自定义 Filter 和 Score，实现特殊资源调度。
>
> 对于 GPU，默认 Scheduler 主要依据 `nvidia.com/gpu` 等扩展资源进行数量调度，不会直接选择具体 GPU 编号。
>
> 如果需要根据显存、GPU 型号、NVLink 拓扑等信息进行调度，可以结合设备发现、调度插件和 DRA 等机制扩展。
>
> 此外，AI Infra 还需要处理 GPU 资源碎片化、多租户隔离、分布式任务的 Gang Scheduling，以及调度器资源账本和节点实际设备分配之间的一致性。

| ---------------------------------- | ------------------------------------------------------ |
| Filter 和 Score 区别？             | Filter 决定可行性，Score 决定优先级                    |
| Scheduler 如何绑定 Pod？           | 通过 API Server 的 Binding 机制                        |
| Reserve 阶段是否真实占用 GPU？     | 主要预留调度状态，设备实际分配在节点侧完成             |
| 为什么需要调度缓存？               | 降低访问 API Server 的成本，并管理调度中的资源假定状态 |
| GPU 数量够了为什么仍 Pending？     | 可能不满足其他资源、亲和性、污点或拓扑要求             |
| Scheduler 能直接选择 GPU UUID 吗？ | 默认 Scheduler 不负责具体设备选择                      |
| 如何避免 GPU 碎片化？              | 合理放置、队列管理、共享或设备分区                     |
| 为什么需要 Gang Scheduling？       | 避免分布式任务只有部分 Worker 获得资源而无法运行       |

这一题与你已经做过的 CRD 开发联系最紧密，也会深入到 `client-go` 的 List/Watch、SharedInformer、缓存一致性、RateLimitingQueue、Leader Election，以及为什么 Kubernetes Controller 必须实现幂等。



# 4、Controller、Informer、WorkQueue 与 Reconcile

面试官：

> Kubernetes Controller 是如何工作的？为什么使用 Informer 而不是直接 Watch API Server？WorkQueue 有什么作用？Reconcile 为什么必须设计成幂等的？

这道题非常重要。它不仅是 Kubernetes Operator 开发的核心，也涉及分布式系统中的事件驱动、状态一致性、故障恢复和控制面高可用。

## 一、Controller 的本质是什么？

Controller（控制器）的核心职责是：

持续观察系统的实际状态，并采取操作，使实际状态向用户声明的期望状态收敛。

例如：

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx
spec:
  replicas: 3
```

用户声明期望有 3 个副本。

假设当前只有 2 个，Deployment 和 ReplicaSet 相关控制器就会协同创建缺失的副本。

它与传统命令式开发的重要区别在于：

- 命令式：收到请求后执行一次操作。
- 声明式：持续维护一个期望状态，故障后还能重新收敛。

这也是 Kubernetes 能够实现自动恢复的重要基础。

## 二、Controller 的内部架构是什么？

一个典型的 `client-go` Controller 包含以下组件：

需要特别区分三个组件：

| 组件      | 解决什么问题                   |
| --------- | ------------------------------ |
| Informer  | 高效观察资源变化，维护本地缓存 |
| WorkQueue | 缓冲、去重、调度待处理资源     |
| Reconcile | 对比状态并执行实际控制逻辑     |

## 三、Informer 为什么不直接调用 Watch？

这是面试高频追问。

你当然可以直接使用：

```
client.CoreV1().
    Pods(namespace).
    Watch(ctx, metav1.ListOptions{})
```

但在完整 Controller 中，需要自己处理许多问题：

- 初次全量资源获取。
- Watch 连接中断。
- ResourceVersion 管理。
- Watch 历史过期。
- 事件与本地状态同步。
- 多个处理器重复 Watch 同一种资源。
- 缓存和事件分发。

Informer 把这些通用问题封装起来。

### Reflector

Reflector 负责通过 List/Watch 机制获取资源状态和变化。

大致流程：

```
List：获取当前资源
          ↓
记录 ResourceVersion
          ↓
Watch：获取后续变化
          ↓
Watch 中断或过期
          ↓
根据情况重建 Watch / 重新 List
```

### DeltaFIFO

DeltaFIFO 暂存对象变化，通常包括 Added、Updated、Deleted、Sync、Replaced 等变化类型。

它与 Controller 的 WorkQueue 不是同一个东西。

### Indexer

Indexer 是本地缓存，可以根据 Key 或索引快速查找资源。

例如：

```
pod, exists, err := informer.
    GetIndexer().
    GetByKey("default/nginx")
```

相比每次 Reconcile 都向 API Server 发 GET，请求量可以明显降低。

### SharedInformer

多个事件处理器可以共享同一套 List/Watch 和缓存，减少对 API Server 的重复访问。

面试标准回答：Informer 通过 List/Watch、缓存和事件分发机制，降低 API Server 压力，并提高 Controller 对资源变化的处理效率。

但要注意：

Informer 缓存是最终一致的本地观察结果，不保证每次读取都是 API Server 的最新状态。

## 四、WorkQueue 是什么？为什么需要它？

假设同一个 Pod 短时间产生了 100 次 Update Event。

如果每个事件都立即启动一个 goroutine 执行控制逻辑，可能导致重复处理和并发冲突。

WorkQueue 可以缓冲待处理对象。

通常队列中保存资源 Key：

```
default/model-a
default/model-b
default/model-c
```

而不是在队列中保存每一份完整资源对象。

Worker 拿到 Key 后，再从缓存或 API 查询当前状态。

### WorkQueue 的重要特性

1. Key 去重

同一个 Key 被多次加入，队列会合并部分重复处理需求，避免简单的一事件一执行。

但并不保证对象只处理一次：如果处理期间又发生更新，完成后可能需要再次处理。

2. 并发消费

多个 Worker 可以从 WorkQueue 获取不同的 Key 并发处理。

3. 失败重试

可以使用带限速能力的队列，让失败对象稍后重新入队。

需要区分：限速队列只是提供重试调度机制，业务代码还要决定何时重试以及何时放弃。

### 一个典型 Worker

```
func (c *Controller) processNextItem() bool {
    key, shutdown := c.queue.Get()
    if shutdown {
        return false
    }

    defer c.queue.Done(key)

    err := c.reconcile(key)
    if err != nil {
        c.queue.AddRateLimited(key)
        return true
    }

    c.queue.Forget(key)
    return true
}
```

其中：

- `Get()`：获取待处理对象。
- `Done()`：表示本次处理结束。
- `AddRateLimited()`：失败后限速重试。
- `Forget()`：清除该 Key 的重试记录。

## 五、Reconcile 为什么必须幂等？

这道题是 Controller 设计的核心。

幂等（Idempotency）指同一操作重复执行时，不会造成超出预期的重复副作用。

假设 `ModelDeployment` 要求有一个模型服务。

错误设计：

```
func Reconcile() error {
    return createDeployment()
}
```

每次执行都尝试创建一个新的、随机命名的 Deployment，就可能不断创建重复资源。



正确思路是先检查状态：

```
func Reconcile() error {
    current := getDeployment()

    if current == nil {
        return createDeployment()
    }

    if needsUpdate(current) {
        return updateDeployment()
    }

    return nil
}
```

实际 Controller 应根据资源的期望状态和实际状态做确定性处理，还需要考虑 API 错误、并发修改和删除流程。

正确思路是：

读取当前对象。

读取相关子资源状态。

对比期望与实际状态。

只执行必要的变更。

使用 OwnerReference、资源版本等机制正确管理对象。

更新 Status，并在必要时重新入队。

### 为什么 Reconcile 可能执行多次？

主要原因：

1. Informer 事件可能重复触发。
2. WorkQueue 失败重试。
3. Controller 重启后重新同步。
4. 周期性 Requeue。
5. 多个关联资源变化。
6. 之前的外部操作已经成功，但返回结果丢失。

因此 Controller 不能假设：

> 一个事件只会触发一次 Reconcile。

这是非常重要的工程原则。

## 六、Informer 缓存不一致怎么办？

假设 Controller 刚刚创建了 Deployment。

随后立刻从 Informer Cache 读取：

```
deployment, err := lister.
    Deployments(namespace).
    Get(name)
```

有可能暂时读取不到。

因为写操作已经提交到 API Server，但本地 Informer 缓存尚未观察到更新。

这不一定是错误。

典型处理方式：

- 使用确定性的资源名称。
- 将 AlreadyExists 视为可能的正常并发结果。
- 适当重试或 Requeue。
- 通过 `resourceVersion` 等机制处理并发修改。
- 不要把缓存暂时未观察到对象理解为对象一定不存在。

追问：直接调用 API Server GET 是不是就彻底解决一致性问题？

不是。

直接读可以减少某些缓存滞后问题，但在读取和写入之间，资源仍可能被其他客户端修改。

所以依然需要处理乐观并发控制、资源版本冲突和重试。

## 七、Controller 高可用如何实现？

假设部署三个 Controller 副本：

```
Controller A
Controller B
Controller C
```

是否让三个副本都执行 Reconcile？

取决于具体架构。

### 方案一：Leader Election

常见 Operator 部署方式是：

```
Controller A：Leader，执行 Reconcile
Controller B：Standby
Controller C：Standby
```

通常使用 Kubernetes Lease 资源进行选主。

Leader 失效后，其他副本可以接管。

这种方式相对简单，适合很多 Operator。

### 方案二：多副本分片执行

也可以把不同资源分配给不同 Controller 实例。

例如：

```
Controller A：Model A～M
Controller B：Model N～Z
```

这种设计可以提高吞吐量，但需要实现分片、重分配和故障接管。

### Leader Election 是否保证绝对不会重复操作？

不能。

例如旧 Leader 因网络分区失去 Lease，但仍然在执行某个外部任务，新 Leader 此时也开始工作。

因此涉及外部系统时，还需要：

- 幂等操作。
- Fencing Token。
- 任务状态持久化。
- 实际状态重新确认。

## 八、实际设计题：ModelDeployment Controller

假设定义 CRD：

```
apiVersion: ai.example.com/v1
kind: ModelDeployment
metadata:
  name: qwen-model
spec:
  model: qwen
  image: example/vllm:latest
  replicas: 2
  gpu: 1
```

Controller 要求：

- 创建模型 Deployment。
- 创建 Service。
- 监控 Ready 状态。
- 模型配置变化时更新工作负载。
- 删除 CRD 时清理资源。

一个合理的 Reconcile 流程：

```
读取 ModelDeployment
          │
          ▼
判断是否正在删除
          │
          ├── 是 → Finalizer 清理
          │
          ▼
构造期望 Deployment
          │
          ▼
CreateOrUpdate
          │
          ▼
构造期望 Service
          │
          ▼
CreateOrUpdate
          │
          ▼
检查 Deployment Status
          │
          ▼
更新 ModelDeployment Status
```

可以使用 `controller-runtime`：

```
func (r *ModelDeploymentReconciler) Reconcile(
    ctx context.Context,
    req ctrl.Request,
) (ctrl.Result, error) {
    var model ModelDeployment

    if err := r.Get(
        ctx,
        req.NamespacedName,
        &model,
    ); err != nil {
        return ctrl.Result{}, client.IgnoreNotFound(err)
    }

    if !model.DeletionTimestamp.IsZero() {
        return r.reconcileDelete(ctx, &model)
    }

    if err := r.reconcileDeployment(ctx, &model); err != nil {
        return ctrl.Result{}, err
    }

    if err := r.reconcileService(ctx, &model); err != nil {
        return ctrl.Result{}, err
    }

    if err := r.reconcileStatus(ctx, &model); err != nil {
        return ctrl.Result{}, err
    }

    return ctrl.Result{}, nil
}
```

这是 Controller 骨架示例，依赖自定义类型与其他方法实现。

真实项目还应考虑：

- OwnerReference。
- Finalizer。
- Status Conditions。
- ObservedGeneration。
- ResourceVersion Conflict。
- 错误重试与退避。
- Workload 关联资源 Watch。
- 多租户权限。

## 十、90 秒面试参考答案

> Kubernetes Controller 的核心是 Reconcile，也就是持续比较期望状态和实际状态，使实际状态向期望状态收敛。
>
> 典型的 client-go Controller 通过 Informer 监听资源变化。Informer 内部利用 Reflector 的 List/Watch 获取数据，通过 DeltaFIFO 处理资源变化，并维护 Indexer 本地缓存。
>
> 当资源变化时，事件处理器通常把资源 Key 放入 WorkQueue。Worker 从队列获取 Key，再执行 Reconcile。
>
> 使用 WorkQueue 是为了去重、削峰、并发处理和失败重试。
>
> Reconcile 必须设计成幂等的，因为 Kubernetes 事件可能重复，Controller 也可能由于失败、重启或周期性同步多次处理同一个资源。
>
> 对于多副本 Controller，可以通过 Leader Election 或资源分片协调执行，但涉及外部系统时，还需要幂等机制和状态确认。
>
> 如果开发 AI 模型 Operator，我会通过 CRD 描述模型部署期望状态，使用 Reconcile 创建 Deployment、Service 等资源，并通过 Status 记录 Ready 状态和错误信息。

# 5、CRD 与 Operator 的区别及生产级 Operator 设计



面试官：

> CRD 和 Operator 有什么区别？如果让你从零设计一个 AI 模型部署 Operator，你会如何设计 CRD、Controller、Reconcile、Finalizer、Status 和版本升级机制？

这是 Kubernetes 平台和 AI Infra 面试中的核心题目。面试官希望确认的不是你会不会写 YAML，而是你是否理解 如何把 Kubernetes 扩展成一个能够自动管理复杂业务系统的平台。

## 一、CRD、Controller、Operator 分别是什么？

三者属于不同层面的概念。

| 概念       | 定义                     | 主要作用                                               |
| ---------- | ------------------------ | ------------------------------------------------------ |
| CRD        | CustomResourceDefinition | 扩展 Kubernetes API，定义新的资源类型                  |
| CR         | Custom Resource          | 根据 CRD 创建的自定义资源实例                          |
| Controller | 控制器                   | 观察资源变化，执行状态收敛                             |
| Operator   | 运维自动化模式及其实现   | 将特定领域的部署、管理、升级、恢复等知识编码为控制逻辑 |

可以简单理解：

CRD 定义管理什么，Controller 实现如何管理，Operator 将这些能力组合成自动化的应用运维系统。

概念关系图。Operator 不一定必须使用 CRD，但 Kubernetes Operator 通常通过 CRD 暴露声明式接口。

### 追问：只有 CRD，没有 Controller，可以吗？

可以。

Kubernetes 允许通过 CRD 扩展 API 资源，即使没有 Controller，也可以对这些资源进行 CRUD、Watch、权限控制等操作。

但是不会自动产生业务控制行为。

例如创建：

```
apiVersion: ai.example.com/v1
kind: ModelDeployment
metadata:
  name: qwen-model
spec:
  replicas: 2
```

如果没有 Controller，这个对象通常只是存储在 Kubernetes API 中的一份自定义资源，并不会自动创建模型服务 Pod。

## 二、如何设计 ModelDeployment CRD？

我会首先区分两部分：

- `spec`：用户希望模型服务达到什么状态。
- `status`：系统观察到模型服务目前处于什么状态。

例如：

```
apiVersion: ai.example.com/v1
kind: ModelDeployment
metadata:
  name: qwen-model
  namespace: ai-team
spec:
  model:
    uri: s3://models/qwen/
  runtime:
    image: registry.example.com/vllm:v1
  replicas: 2
  resources:
    gpu: 1
    memory: 32Gi
```

这里是自定义资源实例的示例，不是完整的 CRD 定义文件。

CRD 的 Schema 可以定义：

- 字段类型。
- 必填字段。
- 枚举。
- 数值范围。
- 默认值。
- 字段校验规则。

比如限制 `replicas` 非负、GPU 请求为非负整数，以及限制模型 URI 的格式。

### 为什么不直接让用户创建 Deployment？

因为 Deployment 只能提供通用的工作负载管理能力。

模型部署还涉及更多领域逻辑：

- 模型地址和版本。
- GPU 资源需求。
- 推理框架。
- 权重下载和缓存。
- 模型加载完成检查。
- 推理端点创建。
- 模型版本升级。
- 部署失败原因。

Operator 可以将这些逻辑封装起来，让用户只声明“部署什么模型”，不需要了解所有 Kubernetes 底层资源。

## 三、Reconcile 怎么实现？

核心流程：

```
读取 ModelDeployment
          │
          ▼
检查删除状态
          │
     ┌────┴────┐
     ▼         ▼
   删除中     正常状态
     │         │
     ▼         ▼
Finalizer   构造期望资源
清理流程        │
               ▼
       Create / Update
               │
               ▼
       观察实际 Workload
               │
               ▼
           更新 Status
```

使用 `controller-runtime` 的典型骨架：

```
func (r *ModelReconciler) Reconcile(
    ctx context.Context,
    req ctrl.Request,
) (ctrl.Result, error) {

    var model aiv1.ModelDeployment

    err := r.Get(ctx, req.NamespacedName, &model)
    if client.IgnoreNotFound(err) != nil {
        return ctrl.Result{}, err
    }
    if apierrors.IsNotFound(err) {
        return ctrl.Result{}, nil
    }

    if !model.DeletionTimestamp.IsZero() {
        return r.reconcileDelete(ctx, &model)
    }

    if err := r.reconcileWorkload(ctx, &model); err != nil {
        return ctrl.Result{}, err
    }

    if err := r.reconcileService(ctx, &model); err != nil {
        return ctrl.Result{}, err
    }

    if err := r.reconcileStatus(ctx, &model); err != nil {
        return ctrl.Result{}, err
    }

    return ctrl.Result{}, nil
}
```

面试中要主动解释：

Reconcile 应该是幂等的、可重试的、能够从中间状态恢复的。

假设创建 Deployment 成功，但更新 Status 失败。

下一次 Reconcile 不能重新创建一个随机命名的 Deployment，而应该通过确定性名称和 OwnerReference 识别已有资源，然后继续状态同步。

## 四、OwnerReference 和 Finalizer 有什么区别？

这是 Operator 面试的高频题。

### OwnerReference：管理 Kubernetes 对象之间的从属关系

例如：

```
ModelDeployment
       │
       ▼
   Deployment
       │
       ▼
   ReplicaSet
       │
       ▼
      Pods
```

如果模型 CR 被删除，Kubernetes Garbage Collector 可以按照删除传播策略清理符合条件的从属对象。

OwnerReference 适合管理 Kubernetes 内部的资源依赖关系。

### Finalizer：处理删除前必须完成的清理工作

假设 ModelDeployment 创建了外部对象存储目录、负载均衡配置，或者注册了外部推理端点。

这些外部资源不能仅靠 Kubernetes Garbage Collector 清理。

可以使用 Finalizer：

```
metadata:
  finalizers:
    - ai.example.com/finalizer
```

删除流程：

1. 用户执行删除。
2. API Server 设置 `deletionTimestamp`。
3. 对象进入删除中状态，但尚未最终消失。
4. Controller 检测到删除事件。
5. 执行外部资源清理。
6. 清理完成后移除 Finalizer。
7. Kubernetes 最终删除对象。

追问：如果 Controller 在清理一半时崩溃怎么办？

重新启动后继续执行 Finalizer 流程。

所以清理操作同样必须幂等。

例如外部资源已经不存在，应该将其视为清理完成，而不应该无限报错。

注意：Finalizer 不是在删除后执行的回调，而是阻止对象在完成清理前被最终删除的机制。

## 五、Status 应该如何设计？

一个生产级 Operator 不应该只使用一个简单的 `Running` 布尔值。

可以设计：

```
status:
  observedGeneration: 3
  phase: Loading
  readyReplicas: 1
  conditions:
    - type: Available
      status: "False"
      reason: ModelLoading
      message: "Waiting for model weights to load"
```

这里最值得了解的是两个概念。

### ObservedGeneration

`metadata.generation` 通常在期望配置发生变化时增加。

`status.observedGeneration` 用于表示 Controller 已经处理或观察到哪个版本的期望配置。

例如：

```
metadata.generation = 5
status.observedGeneration = 4
```

表示 Status 反映的状态可能仍然对应旧版本配置。

因此不能简单因为旧的 `Ready=True` 就认为新模型版本已经部署成功。

### Conditions

Conditions 更适合表达可组合的状态信息，例如：

- Available
- Progressing
- Degraded
- Ready

每个 Condition 可以包含：

- `type`
- `status`
- `reason`
- `message`
- `lastTransitionTime`
- `observedGeneration`

对于 AI 推理平台，Pod Running 不代表模型 Ready，所以 Status 设计尤为重要。

## 六、Admission Webhook 有什么用？

Kubernetes 提供两类常见的准入 Webhook。

| 类型                         | 作用                         |
| ---------------------------- | ---------------------------- |
| Mutating Admission Webhook   | 修改请求对象，例如填充默认值 |
| Validating Admission Webhook | 校验请求是否满足业务规则     |

例如用户创建：

```
spec:
  replicas: 2
  resources:
    gpu: -1
```

可以通过 CRD OpenAPI Schema 或 Validating Admission Webhook 拒绝非法 GPU 数量。

### Schema 与 Webhook 怎么选？

简单字段规则优先使用 CRD Schema。

涉及跨字段、复杂业务规则或外部策略的校验，可以考虑 CEL Validation Rules 或 Webhook。

例如：

> 当推理模式为 tensor-parallel 时，GPU 数量必须满足特定并行配置要求。

但要注意，Admission Webhook 是 API 请求关键路径的一部分。

如果 Webhook 不可用、响应缓慢或配置不合理，就可能影响资源创建和更新。

因此生产环境必须考虑超时、可用性、证书管理及 `failurePolicy`。

## 七、Operator 如何进行版本升级？

这里有两种不同的升级，需要区分。

### 1. Operator 自身升级

例如：

```
Operator v1 → Operator v2
```

重点考虑：

- 新旧 CRD Schema 兼容性。
- Controller 代码兼容性。
- RBAC 权限变化。
- Webhook 兼容性。
- CRD Storage Version。
- 资源版本转换。

如果 CRD 有多个 API 版本，例如：

```
v1alpha1 → v1beta1 → v1
```

字段结构发生不兼容变化时，可能需要 Conversion Webhook。

CRD 的 Served Version 与 Storage Version 不一定相同。

### 2. 模型服务升级

例如：

```
Qwen Model v1 → v2
```

Operator 可以按照期望配置创建新版本的 Deployment。

然后：

1. 下载模型权重。
2. 加载模型。
3. 验证推理服务健康。
4. 灰度切换流量。
5. 观察延迟、错误率。
6. 成功后清理旧版本。
7. 失败则停止切换或回滚。

但对于需要大量 GPU 和显存的大模型，不一定能够同时运行新旧两套完整副本。

因此需要根据实际资源预算选择滚动更新、分批替换或其他升级策略。

## 八、Controller 与 Helm 有什么区别？

这与你之前做的 Chart 开发直接相关。

| 对比                 | Helm                               | Operator                                 |
| -------------------- | ---------------------------------- | ---------------------------------------- |
| 主要目的             | 模板化打包和部署 Kubernetes 资源   | 自动化管理应用生命周期                   |
| 核心机制             | Chart 渲染、Release 管理、升级操作 | Watch、Reconcile、状态收敛               |
| 是否持续控制业务状态 | Helm 本身通常不持续对账            | Controller 可以持续对账                  |
| 自动故障恢复         | 主要依赖部署出的 K8s 资源及控制器  | 可以实现自定义领域恢复逻辑               |
| 开发复杂度           | 相对较低                           | 较高                                     |
| 适用场景             | 常规应用安装、配置、升级           | 复杂有状态系统、模型生命周期、数据库管理 |

举例：

Helm 可以把 vLLM Deployment、Service、ConfigMap 打包成 Chart。

Operator 则可以基于 `ModelDeployment` CR 自动创建和管理这些资源，持续跟踪模型加载状态，并处理特定的升级和恢复流程。

二者不是竞争关系，Operator 也可以使用 Helm Chart 作为底层资源模板的一部分。

## 九、生产级 Operator 最容易忽略的五个问题

| 问题                 | 建议处理方式                                   |
| -------------------- | ---------------------------------------------- |
| Reconcile 被重复执行 | 设计幂等逻辑和确定性资源标识                   |
| Informer 缓存滞后    | 接受最终一致性，处理 AlreadyExists 和 Conflict |
| Controller 重启      | 从持久化的期望和实际状态恢复                   |
| 子资源变化不触发对账 | Watch 关联资源，映射回所属 CR                  |
| Operator 多副本冲突  | Leader Election 或明确的工作分片机制           |

还有一个非常重要的问题：

不要在 Reconcile 中直接执行耗时数十分钟的模型下载操作。

更合理的设计是让 Controller 创建 Job、Pod 或其他异步工作负载来执行下载，并通过状态观察推进下一步。

原因是 Reconcile 应尽量短小、可重试、避免长期占用 Worker。

## 十、面试时 90 秒参考答案

> CRD 用于扩展 Kubernetes API，定义新的资源类型；Controller 通过 Watch 和 Reconcile 使实际状态向期望状态收敛；Operator 则是将特定领域的部署、升级、恢复等运维知识封装成自动化控制逻辑。
>
> 如果开发 AI 模型部署 Operator，我会首先定义 ModelDeployment CRD，使用 Spec 描述模型地址、镜像、GPU 数量和副本数，使用 Status 描述模型部署和加载状态。
>
> Controller 通过 controller-runtime 监听 CR 及相关 Deployment、Service 的变化，执行幂等 Reconcile，创建或更新工作负载，并根据实际 Ready 状态更新 Status。
>
> 对于 Kubernetes 内部资源，可以通过 OwnerReference 管理从属关系；对于需要外部清理的资源，使用 Finalizer 实现可靠删除。
>
> 生产环境还需要考虑 Admission 校验、ObservedGeneration、Conditions、资源版本冲突、故障重试和 Leader Election。
>
> 最后还需要设计 CRD 版本兼容、Operator 自身升级，以及模型版本灰度发布和回滚机制。

## 十一、面试官进一步追问

Q1：CRD 和 Operator 一定要一起使用吗？

不一定。CRD 可以单独存在，Operator 也不一定非要自己定义 CRD。

Q2：Controller 如何知道 Deployment 已经 Ready？

通过读取 Deployment Status，结合 `observedGeneration`、副本数及可用状态判断；对于模型加载完成，还可能需要业务层面的 Readiness。

Q3：为什么不能只靠 Helm？

Helm 擅长部署和 Release 管理，但如果业务需要持续观察模型状态、自动恢复、升级策略等自定义生命周期逻辑，Operator 更适合。

Q4：Finalizer 和 OwnerReference 的区别？

OwnerReference 帮助 Kubernetes 管理资源从属关系和垃圾回收；Finalizer 用于在对象最终删除前执行必要清理。

Q5：Controller 崩溃后如何继续执行？

重新启动后通过 List/Watch 获取资源当前状态，使用幂等 Reconcile 恢复控制过程，而不是依赖上一次函数执行到哪一行。

# 6、Deployment、StatefulSet、DaemonSet 和 Job



面试官：

> Kubernetes 有 Deployment、StatefulSet、DaemonSet、Job 等工作负载控制器，它们有什么区别？
>
> 如果让你设计一个 AI 平台，分别需要部署在线推理服务、分布式训练任务、GPU 监控组件和模型下载任务，你会选择哪些工作负载？为什么？

这道题考察的重点不是记住各个资源的定义，而是根据 AI 工作负载的生命周期、状态管理、资源需求和故障恢复特性，选择合适的控制器。

## 一、四种工作负载的核心区别

| 资源        | 核心功能                         | 典型 AI Infra 场景           |
| ----------- | -------------------------------- | ---------------------------- |
| Deployment  | 维护长期运行的无状态副本         | 在线模型推理 API             |
| StatefulSet | 提供稳定身份、有序管理和存储关联 | 需要稳定节点身份的有状态服务 |
| DaemonSet   | 在符合条件的节点上运行 Pod       | GPU Exporter、Device Plugin  |
| Job         | 执行有限任务，直到成功完成       | 训练、模型转换、批量评估     |
| CronJob     | 按计划创建 Job                   | 定期评估、数据清理、模型同步 |

Deployment

Replica 1

## 二、Deployment：为什么适合在线推理服务？

Deployment 适合需要持续运行、维持一定副本数的服务。

例如部署两个 vLLM 推理实例：

```
apiVersion: apps/v1
kind: Deployment
metadata:
  name: vllm-server
spec:
  replicas: 2
  selector:
    matchLabels:
      app: vllm
  template:
    metadata:
      labels:
        app: vllm
    spec:
      containers:
        - name: vllm
          image: vllm/vllm-openai:v0.8.5
          args:
            - --model
            - /models/my-model
          resources:
            limits:
              nvidia.com/gpu: 1
          readinessProbe:
            httpGet:
              path: /health
              port: 8000
            periodSeconds: 10
          volumeMounts:
            - name: models
              mountPath: /models
      volumes:
        - name: models
          persistentVolumeClaim:
            claimName: model-storage
```

这是示意配置：模型路径、镜像版本、探针以及 PVC 的实际访问能力需要根据环境验证；两个 Pod 能否同时挂载该 PVC 取决于存储后端、访问模式和调度位置。

### Deployment 的核心能力

1. 维护期望副本数量。
2. Pod 异常退出时重新创建。
3. 支持滚动升级。
4. 支持回滚到历史 ReplicaSet 配置。
5. 通过 ReplicaSet 管理 Pod。

控制关系：

```
Deployment
    │
    ▼
ReplicaSet
    │
    ├── Pod 1
    ├── Pod 2
    └── Pod 3
```

### 面试追问：Deployment 是否保证服务高可用？

不保证。

假设两个推理 Pod 都调度到同一 GPU 节点，该节点故障后，两个实例可能同时不可用。

因此还需要：

- Pod Anti-Affinity 或 Topology Spread。
- 多节点 GPU 资源。
- Readiness Probe。
- Service 或推理网关路由。
- 合理的 PodDisruptionBudget。
- 模型加载和预热机制。

Deployment 保证的是副本状态收敛，不等于端到端服务高可用。

## 三、StatefulSet：适合什么 AI 工作负载？

StatefulSet 适合需要稳定网络身份、稳定存储关联或有序生命周期管理的应用。

例如：

```
StatefulSet: training-coordinator

training-coordinator-0
training-coordinator-1
training-coordinator-2
```

StatefulSet 通常提供：

- 稳定 Pod 名称和序号。
- 稳定网络身份。
- 与 Pod 关联的 PVC。
- 可配置的有序部署与更新行为。

### StatefulSet 与 Deployment 最大区别

假设 Pod 被删除后重新创建：

Deployment：

```
model-6b7df8-abc12
        ↓
model-6b7df8-xyz45
```

Pod 名称通常变化。

StatefulSet：

```
model-0
   ↓
model-0
```

Pod 身份通常保持稳定。

### 面试追问：分布式训练是否一定使用 StatefulSet？

不一定，而且不应该默认使用 StatefulSet。

大多数有限时长的训练任务更自然地属于 Job 类工作负载。

StatefulSet 适合长期运行、需要稳定身份的服务；训练作业更需要表达：

- 执行成功或失败。
- 重试次数。
- 完成条件。
- 作业生命周期。
- 多 Worker 协同完成。

如果训练框架有稳定身份需求，可以在专用训练 Operator 中实现相应的 Worker 管理机制，而不是因为存在多个 Worker 就直接选择 StatefulSet。

## 四、DaemonSet：为什么 GPU Device Plugin 通常使用它？

DaemonSet 用于确保符合条件的节点上运行一个相应的 Pod。

例如：

```
GPU Node A → NVIDIA Device Plugin
GPU Node B → NVIDIA Device Plugin
GPU Node C → NVIDIA Device Plugin
```

当新 GPU 节点加入集群后，DaemonSet Controller 可以为其创建相应的插件 Pod。

典型应用：

- NVIDIA Device Plugin。
- DCGM Exporter。
- Node Exporter。
- 日志采集 Agent。
- 节点级网络或存储组件。

### 面试追问：所有 DaemonSet 都会部署到所有 Node 吗？

不会。

可以通过：

- NodeSelector。
- Node Affinity。
- Tolerations。

控制符合部署条件的节点。

例如 GPU 监控组件通常只需要部署到 GPU 节点。

## 五、Job：为什么更适合模型训练？

Job 的主要职责是管理一个最终会完成的任务。

例如运行一次模型训练：

```
apiVersion: batch/v1
kind: Job
metadata:
  name: model-training
spec:
  backoffLimit: 3
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: trainer
          image: pytorch/pytorch:2.5.1-cuda12.4-cudnn9-runtime
          command:
            - python
            - train.py
          resources:
            limits:
              nvidia.com/gpu: 1
```

Job Controller 会观察 Pod 的执行结果，并根据配置管理任务重试和完成状态。

### Job 与 Deployment 的根本区别

Deployment 的目标：

> 持续保持指定数量的 Pod 运行。

Job 的目标：

> 完成指定数量的任务执行。

例如训练程序执行完毕后退出码为 0：

- 对 Job：这通常代表一次成功完成。
- 对 Deployment：Deployment 仍然需要维持服务副本，退出的容器可能被重新启动。

因此有限训练任务适合 Job，而不是 Deployment。

## 六、分布式训练应该如何部署？

假设要使用 4 个节点、每节点 8 张 GPU 执行分布式训练。

总共需要 32 张 GPU。

```
                  Training Job
                        │
                        ▼
                Training Operator
                        │
           ┌────────────┼────────────┐
           ▼            ▼            ▼
        Worker 0      Worker 1      Worker 2 ...
         8 GPU         8 GPU         8 GPU
           │            │            │
           └────────────┼────────────┘
                        ▼
                  NCCL 通信
                        │
                        ▼
               分布式模型训练
```

在生产环境中，通常会考虑使用支持分布式训练的 Operator 或 Job API 扩展，而不是仅使用一个普通 Job 管理所有细节。

需要解决：

1. 多个 Worker 的角色和身份。
2. Rendezvous（进程组协调）。
3. 资源同时可用。
4. Worker 故障后的恢复策略。
5. Checkpoint 保存。
6. 整个训练任务的完成条件。

### 什么是 Gang Scheduling？

假设训练要求 4 个 Worker 同时参与。

但是：

```
Worker 0 → Running
Worker 1 → Running
Worker 2 → Pending
Worker 3 → Pending
```

前两个 Worker 已经占用 16 张 GPU，但训练无法正常开始。

Gang Scheduling 通过协调一组关联 Pod 的调度，尽量避免任务仅获取部分资源并长期占用 GPU。

可以使用 Volcano 等批调度技术，或结合 Kueue 的资源准入和配额管理能力设计整体方案。

需要区分：Kueue 的作业准入和资源配额管理，不等于它独自实现所有节点级 Gang Scheduling 细节。

## 七、模型下载任务应该使用 Job 还是 InitContainer？

这是 AI Infra 系统设计中很好的追问。

假设 vLLM 容器启动前需要下载 20 GB 的模型权重。

### 方案一：InitContainer

```
Pod 启动
    │
    ▼
InitContainer 下载模型
    │
    ▼
主容器启动
    │
    ▼
加载模型到 GPU
```

优点：生命周期与当前 Pod 绑定，实现简单。

缺点：每次创建新 Pod 可能重新下载模型，导致冷启动较慢。

### 方案二：Job 预下载

```
Model Download Job
        │
        ▼
共享模型存储
        │
        ▼
vLLM Deployment
```

优点：模型可以提前准备、独立管理下载进度。

缺点：需要处理任务与部署之间的依赖关系，以及存储并发访问。

### 方案三：节点本地缓存

使用节点级模型缓存或预热机制，将模型权重提前放到 GPU 节点。

这样可以减少大模型冷启动时反复通过网络下载权重的成本。

我的选择：

小型模型或简单平台可以使用 InitContainer；大型模型、多副本平台更值得设计共享存储、节点缓存和预加载能力。

## 八、在线推理 Deployment 如何进行滚动升级？

假设：

```
vLLM v1 → vLLM v2
```

Deployment 默认提供 RollingUpdate 策略。

例如：

```
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 0
```

这意味着升级过程中允许创建额外 Pod，同时尽量维持原有可用副本数。

但是对于 GPU 推理服务存在一个特殊问题：

如果 GPU 已经全部分配完毕，就没有额外资源启动新版本。

例如：

```
Node A：1 GPU，正在运行 vLLM v1
Node B：1 GPU，正在运行 vLLM v1

集群没有剩余 GPU
```

此时 `maxSurge=1` 创建的新 Pod 可能一直 Pending。

而 `maxUnavailable=0` 又不允许先减少旧副本，导致升级无法继续推进。

解决方案可能包括：

- 预留升级所需 GPU 容量。
- 采用允许部分暂时不可用的滚动策略。
- 分批迁移流量。
- 利用可支持共享的 GPU 资源策略。
- 在可接受停机的业务场景下采用 Recreate。

这一题的关键是理解：Kubernetes 的标准滚动升级策略，并没有自动解决 GPU 容量不足的问题。

## 九、PodDisruptionBudget 能解决节点故障吗？

不能完全解决。

PDB 主要限制受控的自愿性驱逐，例如某些节点维护场景。

它不能阻止物理节点突然宕机。

例如：

```
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: inference-pdb
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: inference
```

这个 PDB 要求在遵守 Eviction API 的自愿驱逐流程中尽量保持至少两个可用 Pod。

但是：

- 节点直接故障可能导致多个 Pod 同时不可用。
- PDB 不能保证 Pod 一定能够重新调度。
- PDB 不会自动为模型预留 GPU。
- Deployment 滚动升级有自己的更新控制机制，不应认为 PDB 会直接约束所有升级操作。

# 7、Device Plugin、GPU Operator 与 GPU 资源管理



第二轮进度：6 / 10

核心题

面试官：

> Kubernetes 本身不认识 NVIDIA GPU，那么 GPU 是如何被发现、注册和分配的？
>
> Device Plugin、NVIDIA Driver、Container Toolkit 和 GPU Operator 分别负责什么？
>
> 如果服务器执行 `nvidia-smi` 正常，但 Kubernetes 看不到 `nvidia.com/gpu`，你会如何排查？

这道题最重要的是理解：GPU 能在 Linux 上使用、Kubernetes 能调度 GPU、容器能真正访问 GPU，是三个不同层次的问题。

## 一、先区分五个核心组件

| 组件                     | 职责                                    | 工作层次               |
| ------------------------ | --------------------------------------- | ---------------------- |
| NVIDIA Driver            | 驱动 GPU 硬件，提供计算能力             | Linux 内核及用户态驱动 |
| NVIDIA Container Toolkit | 帮助容器运行时配置 GPU 设备访问         | 容器运行时             |
| NVIDIA Device Plugin     | 向 Kubelet 注册和报告 GPU，配合设备分配 | Kubernetes 节点资源    |
| NVIDIA GPU Operator      | 自动部署和管理整套 NVIDIA GPU 软件组件  | Kubernetes 控制面      |
| DCGM Exporter            | 采集 GPU 利用率、显存、温度等指标       | 可观测性               |

NVIDIA 官方将这些组件组合为 GPU Operator 管理的软件栈，包括驱动、Toolkit、Device Plugin、GPU Feature Discovery 和监控组件。

NVIDIA GPU Operator+1



这里最容易混淆的是：

Device Plugin 不是 GPU Operator。

Device Plugin 主要负责设备资源注册与分配接口；GPU Operator 则负责管理这些组件的部署、配置和生命周期。

## 二、GPU 从物理硬件到 Pod 的完整链路

这是传统 Device Plugin 路径的逻辑示意。GPU Operator 在旁负责管理相关软件组件，而不是逐个接管 Pod 的实时调度。

### 第一步：Linux 识别 GPU

驱动安装成功后，在节点执行：

```
nvidia-smi
```

如果能够正常显示 GPU 型号、显存和驱动版本，说明主机层面至少能够通过 NVIDIA 管理接口访问 GPU。

但这只能证明主机驱动链路基本正常，不能证明 Kubernetes 已经注册 GPU。

### 第二步：Device Plugin 注册 GPU

Device Plugin 通过 Unix Socket 和 gRPC 向 Kubelet 注册。

典型目录：

```
/var/lib/kubelet/device-plugins/
```

关键接口包括：

| 接口         | 职责                               |
| ------------ | ---------------------------------- |
| Register     | 向 Kubelet 注册插件及资源名        |
| ListAndWatch | 报告设备列表和健康状态             |
| Allocate     | 返回容器使用指定设备所需的配置信息 |

Kubelet 将 GPU 资源反映到 Node Status 中。

Kubernetes Contributors



例如：

```
status:
  capacity:
    nvidia.com/gpu: "8"
  allocatable:
    nvidia.com/gpu: "8"
```

`capacity` 是节点报告的资源容量；`allocatable` 是可用于 Pod 调度核算的资源量。

这里的 `allocatable: 8` 并不意味着当前还有 8 张空闲 GPU。已经由 Pod 请求的 GPU 还需要单独核算。

### 第三步：Scheduler 选择节点

用户创建：

```
apiVersion: v1
kind: Pod
metadata:
  name: gpu-test
spec:
  restartPolicy: Never
  containers:
    - name: cuda
      image: nvidia/cuda:12.6.3-base-ubuntu24.04
      command: ["nvidia-smi"]
      resources:
        limits:
          nvidia.com/gpu: 2
```

Scheduler 检查哪个 Node 满足两张 GPU 的资源请求。

但是，标准调度流程主要选择 Node，并不负责决定 GPU 0、GPU 1 还是 GPU 5。

### 第四步：Kubelet 分配具体设备

Pod 绑定节点后，Kubelet 的 Device Manager 选择具体可用设备，并调用插件的 `Allocate`。

例如它选择了两张 GPU：

```
GPU UUID A
GPU UUID C
```

Device Plugin 返回设备分配相关信息，例如设备节点、环境变量、挂载或 CDI 设备引用。

### 第五步：容器真正使用 GPU

Container Runtime 根据设备分配配置，在 NVIDIA Container Toolkit 或相应 CDI 集成的配合下，使容器获得 GPU 访问能力。

最终容器内的 CUDA 程序才可以使用已分配的 GPU。

因此必须区分：

设备发现 → 资源调度 → 设备分配 → 容器设备接入。

它们不是同一步。

## 三、GPU Operator 的原理是什么？

面试官追问：

> 已经有 NVIDIA Device Plugin 了，为什么还需要 GPU Operator？

因为 Device Plugin 不负责整个 GPU 软件环境的安装和维护。

假设一个集群有 100 台 GPU 服务器，需要配置：

- 兼容的 GPU Driver。
- NVIDIA Container Toolkit。
- Kubernetes Device Plugin。
- GPU 型号及能力标签。
- GPU 监控。
- MIG 配置。

如果全部依靠运维脚本逐台安装，版本兼容、升级、节点替换和故障修复的成本会很高。

GPU Operator 将这些能力声明式地管理起来。

GPU Operator 一般通过 CRD、Controller、DaemonSet 等 Kubernetes 机制管理组件。

这和前面讲的 Operator 原理是一致的。

你可以把 GPU Operator 理解为针对 NVIDIA GPU 软件栈实现的专用运维 Operator。

NVIDIA 也支持在节点已经预装驱动的情况下关闭 Operator 的驱动安装功能，避免重复管理。

NVIDIA GPU Operator



## 四、面试实战：nvidia-smi 正常，但 Kubernetes 看不到 GPU

这是本题最重要的工程排查部分。

我会按照故障所在层次，从下到上排查。

### 1. 主机驱动层

```
nvidia-smi
lsmod | grep nvidia
ls -l /dev/nvidia*
```

确认驱动已经加载、设备节点存在，且 GPU 能被主机识别。

### 2. Device Plugin 层

```
kubectl get pods -A | grep -E 'nvidia|gpu'
```

再查看具体 Device Plugin Pod：

```
kubectl describe pod <device-plugin-pod> -n <namespace>
kubectl logs <device-plugin-pod> -n <namespace>
```

重点判断：

- 插件是否运行。
- 能否访问 GPU 设备。
- NVML 初始化是否成功。
- 是否与驱动版本兼容。
- 是否已向 Kubelet 注册。

### 3. Kubelet 注册层

查看节点资源：

```
kubectl describe node <node-name>
```

重点检查：

```
Capacity:
  nvidia.com/gpu: 8

Allocatable:
  nvidia.com/gpu: 8
```

如果完全没有 `nvidia.com/gpu`，优先检查 Device Plugin 注册和健康报告。

检查节点上的插件 Socket：

```
sudo ls -l /var/lib/kubelet/device-plugins/
```

然后查看 Kubelet 日志：

```
sudo journalctl -u kubelet -n 200 --no-pager
```

在 K3s 等发行版中，Kubelet 可能内嵌于其服务进程，日志位置应按实际部署方式调整。

### 4. 容器运行时层

如果 Node 已经能看到 GPU，但容器无法使用，就要检查运行时。

例如：

```
nvidia-ctk --version
```

以及 containerd 的 NVIDIA 运行时配置、CDI 配置、相关 RuntimeClass 和容器启动日志。

需要特别注意：能正常调度 GPU，不代表容器一定能访问 GPU。

### 5. 工作负载层

检查 Pod 资源声明：

```
kubectl describe pod gpu-test
```

如果 Pod Pending，先看调度 Events。

如果 Pod 已运行但 CUDA 初始化失败，则转向驱动、设备注入、镜像 CUDA 运行时兼容性和容器权限排查。

### 排查结论速查

| 故障现象                    | 优先排查                         |
| --------------------------- | -------------------------------- |
| 主机 `nvidia-smi` 失败      | 驱动、内核模块、硬件             |
| 主机正常，Node 没有 GPU     | Device Plugin、Kubelet 注册      |
| Node 有 GPU，Pod Pending    | 资源请求、亲和性、污点、调度约束 |
| Pod Running，容器看不到 GPU | Toolkit、CDI、Runtime、设备注入  |
| 容器能看到 GPU，CUDA 报错   | 驱动兼容性、CUDA 库、运行环境    |
| GPU 突然从 Allocatable 消失 | 设备健康、插件重启、驱动故障     |

## 五、深入追问：Device Plugin 和 DRA 有什么区别？

这是 AI Infra 工程师应该了解的新一代设备管理机制。

传统 Device Plugin 的资源声明方式：

```
resources:
  limits:
    nvidia.com/gpu: 2
```

优点是简单，可以直接使用 Kubernetes 扩展资源调度。

但缺点是：`nvidia.com/gpu: 2` 只描述资源数量，并没有直接表达 GPU 型号、显存容量和拓扑等复杂条件。

### Dynamic Resource Allocation（DRA）

DRA 是 Kubernetes 更灵活的设备资源分配机制。

它可以使用 DeviceClass、ResourceClaim、ResourceSlice 等对象表达和匹配设备需求。

例如，希望申请的是：

```
GPU 数量：2
GPU 型号：特定系列
显存容量：满足模型要求
```

不只是简单的数量 2。

DRA 在 Kubernetes v1.35 成为稳定功能，但具体设备选择能力仍取决于驱动实现和集群版本。

Kubernetes



NVIDIA 也提供了 DRA GPU 驱动，支持按设备属性选择 GPU 等能力。

NVIDIA GPU Operator



### 对比

| 对比         | Device Plugin 扩展资源 | DRA                        |
| ------------ | ---------------------- | -------------------------- |
| 主要资源表达 | 整数数量               | 设备声明与属性匹配         |
| GPU 型号筛选 | 通常结合 Node 标签     | 可通过设备属性匹配         |
| 具体设备管理 | Kubelet Device Manager | DRA 资源分配机制           |
| 适用场景     | 常规 GPU Pod           | 更复杂的设备选择与共享需求 |

注意：DRA 不等于 GPU 自动虚拟化。 设备能否被共享、隔离和切分，仍取决于硬件、驱动及对应的资源管理实现。

## 六、深入追问：GPU Sharing、Time-Slicing、MIG 有什么区别？

面试官：

> 一张 80GB 显存的 GPU，两个模型各只需要 20GB 显存，能不能让它们共享这张 GPU？

可以考虑，但不能简单认为把 `nvidia.com/gpu` 设置成 0.5 就能实现。

| 机制         | 工作原理                      | 隔离能力         |
| ------------ | ----------------------------- | ---------------- |
| Time-Slicing | 多个任务分时共享 GPU          | 较弱             |
| MPS          | 多 CUDA 进程共享 GPU 执行资源 | 取决于配置及硬件 |
| MIG          | 将支持的 GPU 分成独立硬件实例 | 相对更强         |
| vGPU         | 通过虚拟化机制提供虚拟 GPU    | 取决于实现       |

尤其要注意：

Time-Slicing 不会自动把物理显存切成相互隔离的固定份额。

如果两个模型都尝试使用大量显存，仍然可能竞争资源，甚至出现 OOM。

MIG 能够提供更明确的硬件资源分区，但只适用于支持 MIG 的 GPU。

因此，生产级共享 GPU 调度不仅是让两个 Pod 同时进入节点，还要考虑显存预算、租户隔离、故障影响与资源计量。

## 七、AI Infra 系统设计追问

面试官：

> 假设你负责一个拥有 100 台 GPU 服务器的 AI 平台，如何管理这些 GPU 节点？

我会分成三个控制层次：

基础设施层：GPU Operator

管理驱动、Toolkit、Device Plugin、设备标签和 DCGM 监控，确保节点可以稳定提供 GPU 资源。

资源调度层：Scheduler / DRA / 队列

管理 GPU 型号、数量、拓扑、队列、优先级、租户配额和资源碎片化问题。

业务控制层：Model Operator

管理模型部署、权重加载、推理副本、健康检查、扩缩容、版本升级和故障恢复。

这三个层次需要协作，但不应该混为一谈。

例如，Model Operator 负责声明某个模型需要 4 张 GPU，却不应该自行替代底层驱动管理，也不必自己实现所有设备分配细节。

## 八、90 秒面试参考答案

> Kubernetes 通过 Device Plugin Framework 支持 GPU 等特殊硬件。
>
> NVIDIA Device Plugin 运行在 GPU 节点上，使用 gRPC 向 Kubelet 注册 `nvidia.com/gpu`，并通过 ListAndWatch 报告设备和健康状态。
>
> Kubelet 将 GPU 资源更新到 Node Status，Scheduler 根据 Pod 的扩展资源请求选择节点。
>
> Pod 绑定后，Kubelet 通过设备管理机制选择具体 GPU，调用 Device Plugin 的 Allocate 接口获取设备配置，再由容器运行时配合 NVIDIA Container Toolkit 或 CDI 完成设备接入。
>
> GPU Operator 则是更上层的自动化管理组件，负责部署和维护 NVIDIA Driver、Container Toolkit、Device Plugin、GPU Feature Discovery 和监控等组件。
>
> 如果主机 nvidia-smi 正常，但 Kubernetes 看不到 GPU，我会依次检查 Device Plugin Pod、NVML 初始化、Kubelet 注册日志、Node Capacity 和 Allocatable。
>
> 如果 GPU 已注册，但容器无法使用，则继续检查 Container Runtime、Toolkit、CDI 和设备注入配置。
>
> 对于更复杂的 AI 平台，还需要考虑 GPU Sharing、MIG、DRA、GPU 拓扑和多租户资源隔离。
