# 1、你觉得一个高可用系统应该具备哪些能力？



我会从三个方面理解高可用：

第一是故障预防。 通过多副本、故障域隔离、资源配额、容量规划减少单点故障和级联故障。

第二是故障检测。 通过健康检查、Metrics、Logs、Tracing 和告警快速识别异常。

第三是故障恢复。 通过自动重启、流量切换、Leader Election、故障转移、重试和数据恢复缩短不可用时间。

同时必须明确 RTO 和 RPO。

RTO 是可接受的恢复时间，RPO 是可接受的数据丢失窗口。

对于有状态分布式系统，高可用不能单独考虑，还需要结合数据一致性。

例如发生网络分区时，应该明确系统更优先保证什么操作可继续进行，以及哪些操作需要拒绝，不能简单地让两个节点同时成为主节点。





# 2 分布式系统如何保证消息不重复执行？

参考回答：

严格来说，很多系统在出现超时和故障重试时，无法仅靠消息队列保证业务副作用绝对只发生一次。

工程上常见的方案是 At-Least-Once 消息投递加业务幂等。

例如创建一个云资源时，可以为操作生成唯一 Request ID。

服务端通过数据库唯一约束或状态机保证同一个请求不会重复创建资源。

如果执行跨越数据库和外部系统，则需要设计执行状态、幂等键、结果查询或补偿机制。

对于要求强一致性的操作，可能需要事务或者进一步的协调协议。

At-Least-Once + 幂等消费，可以实现接近业务意义上的 Exactly-Once Effect，但不代表底层消息只投递一次。

# 3 什么是 Backpressure？为什么 P99 延迟很重要？

参考回答：

Backpressure 是当下游处理速度低于上游生产速度时，通过反馈或控制机制避免请求无限堆积。

例如，一个服务每秒收到 10,000 个请求，但只能处理 5,000 个。

如果持续接收所有请求，就会导致队列越来越长，内存增加、延迟升高，最终可能引发服务崩溃。

常见解决方案包括：

- 有界队列、限制并发数。
- 限流和负载丢弃。
- 使用背压协议或消费者按能力拉取。
- 配合超时、熔断和重试预算。

P99 是 99% 请求延迟不超过的分位点。

它比平均延迟更容易反映用户遇到的尾部请求问题，但不代表最大延迟。

例如平均延迟 20ms、P99 为 1s，说明存在明显的尾延迟问题。

我会结合 P50、P95、P99、QPS 和错误率，而不是只观察平均值。

# 4 假设你要设计一个能管理 10 万个 Pod 的云原生控制平台，如何避免 API Server 被打爆？

参考回答：

我会优先避免平台直接对 API Server 进行高频全量轮询。

首先使用 Informer 的 List/Watch 和本地缓存减少重复查询。

其次通过 WorkQueue 合并重复事件、控制 Reconcile 并发、设置限速重试，避免故障时出现重试风暴。

对于资源更新，优先使用局部 Patch，避免不必要的全对象更新，并合理处理 `resourceVersion` 冲突。

还需要考虑：

1. 控制器资源分片，避免单实例维护过多无关资源。
2. 对外部 API 调用做并发控制和限速。
3. 限制不必要的 Status 更新和事件写入。
4. 监控 API Server 请求延迟、429、etcd 延迟和 Watch 断连。
5. 做容量压测，并结合 API Priority and Fairness、etcd 和控制面资源配置进行优化。

这里最关键的是不能简单地通过增加 Controller 副本来提高吞吐量，因为多副本可能进一步增加 API Server 压力，还需要考虑 Leader Election、分片和缓存架构。



# 4 Kubernetes 已经支持 Pod 弹性扩缩容，为什么还需要 Serverless？

Kubernetes 是容器编排系统，而 Serverless 更多是一种计算资源交付和使用模型，两者并不冲突。

Kubernetes 提供基础的调度、扩缩容和容器管理能力。

Serverless 在此基础上进一步抽象资源管理，让用户更多关注代码、函数或者服务，而不是直接管理服务器和容器。

例如常见 Kubernetes HPA 可以根据 CPU、内存或自定义指标调整副本数，但它本身不提供完整的请求缓冲、从零启动、按执行量计费等 Serverless 能力。

Knative Serving 则提供请求驱动的服务伸缩能力，并支持 Scale to Zero。

所以我认为 Serverless 的核心不只是自动扩缩容，而是提高资源利用率、屏蔽基础设施复杂性，并支持按需执行计算任务。

Kubernetes+1



# 5 如果让你优化 Serverless 冷启动，你会怎么做？

参考回答：

首先需要明确冷启动的时间消耗在哪里。

通常包括实例调度、容器或沙箱创建、镜像获取、网络和存储准备、应用初始化等。

我会逐项采集耗时，再选择优化方案：

第一，资源预热。 保留一部分 Warm Pool，减少请求到达后才启动实例的时间。

第二，镜像和运行环境优化。 减少镜像大小、优化镜像拉取、提前准备基础镜像和运行环境。

第三，扩缩容优化。 使用请求并发数、队列长度等业务指标，并结合预测式扩容，避免仅依赖滞后的 CPU 指标。

第四，调度优化。 减少调度路径耗时，合理安排节点资源，避免资源碎片。

第五，合理设置 Scale to Zero 策略。 对高频服务保留最低实例数，对低频服务允许缩容到零。

需要注意的是，预热越多，冷启动越少，但空闲资源成本越高。

因此本质上需要在延迟、资源利用率和成本之间权衡
